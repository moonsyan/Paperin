# Paperin 产品战略发展报告（2026-09-22）

> 审查日期：2026-09-22（Asia/Shanghai）  
> 代码基线：当前 `master`，版本 `0.7.0`，当前 tag：`v0.7.0`  
> 审查范围：代码、架构边界、自动测试、Electron 冒烟、性能、构建、发行配置、文档、用户信息和竞品定位。  
> 本文是 2026-09-21 报告的更新版；上一版保留为历史快照，不作为当前绿灯证据。

## 1. 结论先行

Paperin 已经从“Markdown 编辑器原型”进入“工程化程度较高的个人产品候选”，但还没有进入“可稳定对外承诺的公开版”。当前最准确的阶段是：

> **个人版私有种子验证期，核心功能候选完成，发行与性能证据仍未收敛。**

代码已经形成一套有辨识度的产品骨架：用户打开自己的项目资料，在同一个本地工作区中搜索、引用、写作、保存、维护并交付文档。它比单纯的 Markdown 编辑器多了资料复用和文档生命周期能力，比个人知识库更靠近完整技术/项目文档，比云端知识库更尊重本地文件和离线工作。

但当前不能把以下事实混为产品成熟度：

| 证据层 | 当前结论 |
| --- | --- |
| 代码存在 | Markdown 编辑、工作区、来源引用、索引、版本、恢复、导出和发行流程已经存在 |
| 自动验证 | `typecheck`、lint、223 个测试文件/1603 项测试、build、a11y 和生产依赖审计本轮通过 |
| 真实桌面链路 | `npm run smoke` 本轮通过，覆盖工作区、新建、保存、冲突、重命名、搜索、系统文件关联、来源查找/插入引用、保存重开和资源包导出 |
| 性能证据 | 本轮 `perf:regression` 失败；`perf:production` 的 5000 文件搜索失败，冷索引通过但偏慢 |
| 发行证据 | 候选工作流已配置，Windows 安装/升级/卸载循环仍未验证；当前 Git remote 为 Gitee，GitHub 可达性未验证 |
| 用户价值 | 2 位真实用户，尚无系统任务记录；外部采用、留存、付款和团队需求均未验证 |

下一步不应继续用更多功能扩大产品表面积。最重要的工作是把已有能力变成一条陌生用户可独立完成、结果可信、下一次还会回来使用的核心路径。

## 2. 战略定位

### 2.1 推荐定位

> **Paperin 是面向个人技术写作者和独立开发者的本地 Markdown 项目知识工作台，帮助用户把散落的项目资料写成带来源、可持续维护、可直接交付的文档。**

短表达：

> **把项目资料，写成能交付、能继续维护的文档。**

“通用写作、技术文档维护、项目资料扩展、知识库管理”不是四个互相分散的产品方向，而是同一个任务的不同入口：

```text
打开自己的资料
  -> 找到相关内容和来源
  -> 写成当前结论
  -> 安全保存并继续维护
  -> 交付 Markdown / HTML / PDF / Word 等成果
```

### 2.2 目标用户顺序

第一优先级不是所有 Markdown 用户，而是有真实资料积累、又需要把资料写成成果的人：独立开发者；技术作者、实施和运维人员；维护个人项目知识库的研发人员。后续才是小团队的文档责任人，以及有治理预算的企业知识库团队。

不把“喜欢记笔记的人”作为第一画像，因为 Paperin 当前的独特能力不是随手记，而是把已有资料转化为可靠文档。

### 2.3 产品承诺与非承诺

Paperin 应承诺：

- 用户的 Markdown 和附件仍是普通、可取回的本地文件。
- 来源可以在写作时被找到、插入，并在来源变化后被提醒。
- 保存、冲突、草稿、恢复和导出对用户可解释，不静默覆盖或丢失内容。
- 用户可以用较少配置完成从资料到文档交付的闭环。

Paperin 当前不应承诺比 Obsidian 更强的全能知识管理、比 Typora 更成熟的单篇编辑体验、所有设备和格式无条件兼容、企业级协作/权限/审计，或全库 AI 自动理解。

## 3. 资源、约束与经营假设

| 事项 | 当前事实 | 战略含义 |
| --- | --- | --- |
| 开发投入 | 主要由 AI 完成，人工集中在晚上和周末 | 产码速度不是瓶颈；真实用户、真机、发行和取舍才是瓶颈 |
| 真实用户 | 2 人 | 足以发现阻塞，不足以证明市场、留存或收入 |
| 发布意图 | 希望成熟后面向外部用户，当前设想通过 GitHub 发布 | 先完成可达仓库、候选包和安装证据，再扩大宣传 |
| 当前远端 | `origin` 为 `https://gitee.com/MingProject/FileHome.git` | 与 `package.json`/工作流中的 GitHub 发布目标不一致，必须在 Alpha 前解决 |
| 收费 | 暂无计划 | 先验证重复价值，再做人工小额付款实验，不先做授权系统 |
| 长期方向 | 个人版 -> 外部用户 -> 团队 -> 企业内部知识库 | 每次扩张都必须有进入门槛，不能并行建设四套产品 |

建议把每周可用时间按约 20 小时规划：代码和修复不超过 12–14 小时；至少 4 小时用于真实任务观察、安装/性能验证和发行材料。AI 可以加快实现，但不能代替产品判断、用户授权、数据安全验收和发布责任。

## 4. 当前代码与工程状态

### 4.1 架构判断

当前架构与产品目标匹配，不需要框架迁移：

```text
Renderer (React / Milkdown)
  -> window.desktopAPI
Preload (contextBridge + typed narrow API)
  -> named IPC channels
Main (文件、工作区、索引、窗口、设置、历史、导出)
Shared (DTO、状态、常量、纯逻辑)
```

代码审查的正面结论：Renderer 未直接使用 Electron、Node 内置模块或用户文件系统；Preload 是唯一能力出口；主进程负责路径信任、图片协议、IPC 参数、窗口工作区范围和文件写入安全；保存链路使用 `expectedMtime`/版本检查、串行队列、冲突拒绝和恢复材料；Milkdown/ProseMirror 是正文状态源；工作区索引、标签、反链、图谱、来源健康和发布报告已经分成可测试边界。

继续投入应围绕产品行为和真实环境验证，而不是重写 Electron、React 或编辑器框架。

### 4.2 能力盘点

| 能力域 | 代码中已有 | 当前证据边界 |
| --- | --- | --- |
| Markdown 写作 | GFM、表格、任务列表、代码、公式、Mermaid、脚注、frontmatter、粘贴转换、查找替换 | 真机中文 IME、复杂长期编辑仍未完成矩阵验证 |
| 工作区 | 文件树、外部文件、多标签、固定标签、最近、收藏、路径条、窄窗口抽屉 | 安装态文件关联和升级后数据保留未验证 |
| 资料复用 | 全文/结构搜索、标签、Wiki 链接、反链、关系图、搜索/反链插入来源 | 是否明显节省真实用户时间未知 |
| 来源可信度 | 来源快照、mtime 变化/缺失提示、质量面板、重新定位入口 | 来源移动后的真实用户处理成本未知 |
| 文件可靠性 | 编码检查、冲突保护、保存队列、恢复写入、版本历史、草稿、关闭确认、回收站删除 | 真实磁盘满、权限拒绝、进程终止、跨平台故障矩阵未完成 |
| 交付 | Markdown、HTML、PDF、DOCX、Pandoc、EPUB/LaTeX 入口，HTML 资源包和脱敏交付报告 | 接收方软件、打印、字体和安装态矩阵未完成 |
| 发布配置 | 最多 20 条发布配置，资源包含 `paperin-delivery-report.json` | 交付是否被真实接收方采用未知 |
| 发行 | Windows/macOS/Linux 构建配置、候选 Draft、正式发行显式确认门禁 | 安装、签名、公证、回退、用户文件保留未验证 |
| 团队/企业 | 普通文件可通过 Git、共享目录和现有平台传递 | 身份、权限、审计、评论、审批、实时协作、运维控制面不存在 |

### 4.3 维护成本与技术风险

当前生产代码中仍有多个大文件，功能继续增加会放大 AI 生成代码的回归成本：`editor.css` 1084 行、`settings.css` 677 行、`docx.ts` 559 行、`useAppSettings.ts` 514 行、`useEditorOverlays.ts` 460 行、`useMilkdownInstance.ts` 456 行、`AppComposition.tsx` 438 行。

这不是立即整仓重构的理由。规则应是：触及某一大文件时先拆出明确边界，补直接测试，再继续新增功能；不要让“AI 生成很快”掩盖维护面正在变宽。

### 4.4 体积与启动风险

本轮生产构建成功，但输出显示渲染包较重：Milkdown chunk 约 1.85 MB、主入口约 1.52 MB、Mermaid 核心约 1.18 MB，另有 KaTeX、Cytoscape 和多种图表 chunk。它不等于用户一定感到慢，但应列为体验风险：先测冷启动到可编辑、普通文档、首次 Mermaid/公式和 5 MiB 文档的 P50/P95；如果普通写作被重型图表阻塞，再做按需加载。不以包大小猜测体验。

### 5.2 本轮性能失败

| 命令/夹具 | 本轮结果 | 目标/影响 |
| --- | --- | --- |
| `npm run perf:regression`，5000 篇 × 2048B | 退出 1；tree 332.25ms、index 11713.59ms、search 2079.23ms | 超过 200/2000/1500ms；当前合成回归红灯 |
| `npm run perf:production`，5000 篇真实 Markdown | 退出 1；冷索引 6899.3ms，搜索 P95 13371.8765ms | 搜索超过 5000ms；watcher 20k 事件项通过，P95 1298.07ms |

这说明性能不是“已经解决”的问题，而是“夹具和代码都已存在、当前机器的新鲜搜索证据失败”的问题。下一步必须固定 Node、磁盘、杀毒/索引服务、CPU/RAM 和夹具版本，重复至少三轮；拆分文件发现、读取、解析、过滤、排序、IPC 和渲染等待；确认搜索是否每次重新读盘、是否复用索引；只有根因明确且体验预算合理时才调整实现或阈值。

在 5000 篇搜索门禁解释清楚前，不应宣传 Paperin 面向大型知识库“性能领先”。

### 5.3 发行证据仍未完成

候选发行流程已经设计：tag 或手动触发只生成 Draft，正式发布需要同一 commit、`candidate_sha` 和显式 `PUBLISH`。未完成的是本机 `build:win` 后两个隔离环境的安装/升级/卸载和用户文件保留，macOS 签名/公证，Linux MIME/字体/桌面集成，以及 GitHub 仓库和 Release 的真实可达性。

当前 `git remote -v` 显示 `origin` 是 Gitee，而 `package.json` 和 `.github/workflows/release.yml` 面向 GitHub；本轮访问 GitHub 目标未形成成功可达证据。不要猜测仓库是否存在，但必须在 Alpha 前用真实远端配置和候选 Draft 运行闭环。

## 6. 竞争格局与战略空位

Paperin 面对单篇 Markdown 编辑器、个人知识系统、云端知识库和开发者工具链四类替代方案；用户继续用资源管理器、Git 和复制粘贴也属于竞争。

### 6.1 对照矩阵

| 产品 | 用户主要购买的价值 | Paperin 不应追赶的部分 | Paperin 可占据的相邻位置 |
| --- | --- | --- | --- |
| Obsidian | 本地 Markdown、双链、属性/Bases、插件生态、Sync/Publish | 插件数量、社区和全能个人知识系统 | 更少配置地完成“找资料 -> 插来源 -> 写成稿 -> 交付” |
| 思源笔记 | 中文本地优先、块级引用、数据库、双链、同步扩展 | 块级数据库和复杂知识对象 | 直接维护项目目录中的普通 Markdown，围绕完整文档交付 |
| 语雀 | 结构化知识库、分享、多人编辑、组织沉淀 | 云端协作和组织运营 | 个人离线原稿与资料整理，之后向语雀交付 |
| Typora | 低学习成本的所见即所得单篇写作、导出 | 单篇编辑细节和成熟主题生态 | 跨文档来源复用、持续维护和项目上下文 |
| MarkText | 免费开源、实时预览、轻量 Markdown 编辑 | “免费 Markdown 编辑器”同质竞争 | 工作区、来源、恢复和交付闭环 |
| Notion | 文档、数据库、项目、模板、AI、团队工作区 | 云端全能工作空间和模板市场 | 本地源文件、无账号核心任务、与 Git/同步盘共存 |
| Logseq | 大纲、块引用、日记流、查询和关系 | 块式思考与查询语言 | 连续技术文档、项目目录和最终交付成果 |
| Joplin | 多端笔记、同步、端到端加密 | 跨设备同步基础设施 | 直接维护用户项目文件，而不是应用内笔记数据库 |
| Zettlr | 学术写作、引用管理和多格式输出 | 学术文献生态 | 技术/项目资料引用与交付 |
| VS Code + Git | 代码同仓、Git、扩展、可编程性 | 开发者生态和可编程工具链 | 为不想装配插件的人提供专注的文档工作台 |
| 飞书知识库/Confluence | 权限、协作、评论、审计、组织集成 | 企业治理和实时协作 | 作者先在本地形成可靠成果，再交给团队系统 |
| Outline/GitBook | 托管知识库和面向读者的发布体验 | 托管、站点运营和权限 | 本地创作、维护和导出源文件 |

### 6.2 Paperin 的可防守位置

不要说“Paperin = Typora + Obsidian + 语雀”。更准确的表达是：

> **比 Typora/MarkText 更重视跨文档资料复用和持续维护；比 Obsidian/Logseq 更少配置、更靠近完整成稿；比语雀/Notion/飞书更本地、更尊重原始文件；比 VS Code 更面向文档作者，而不是代码编辑器用户。**

这个位置依赖四个动作被连接起来：资料可发现、资料可引用、文档可维护、成果可交付。只有用户在真实任务中感到这四步减少了返工，定位才是优势；功能存在本身不是优势。

## 7. 产品优势与必须补强的地方

应保留并强化：

- **文件主权。** Markdown、附件和 Git 仍可直接使用，迁入和迁出成本低。
- **来源在写作流中。** 搜索到来源后插入文章，并用快照和变化提示支持可追溯维护。
- **文档生命周期可信。** 冲突拒绝、恢复写入、草稿、关闭保护、版本历史和编码检查建立长期信任。
- **从原稿到交付。** 资源包、导出、预检和脱敏交付报告为个人专业用户提供结果闭环。

必须补强：

1. 性能解释能力：当前 5000 篇搜索门禁失败，必须优先定位。
2. 无帮助激活：两位用户和外部样本需验证 15 分钟独立完成率。
3. 发行可信度：GitHub/Gitee、候选包、安装器、升级回退和数据保留要有可复核记录。
4. 维护成本：建立大文件、包体、测试耗时和警告噪声预算，控制 AI 生成代码的回归面。

## 8. 产品边界与优先级

### 8.1 现在做

- 修复并解释 5000 篇工作区搜索性能红灯。
- 完成 Windows 候选安装/升级/卸载和文件关联循环。
- 解决 GitHub 真实发布渠道与当前 Gitee 远端的配置矛盾。
- 连续两周观察两位现有用户，每人至少 3 次真实任务。
- 只按观察结果优化“找来源、插入、保存重开、导出”的最大阻塞。
- 保持文件安全、来源健康、导出预检和诊断脱敏。

### 8.2 有外部任务证据后做

来源移动/断链的批量重定位；项目文档模板、变更摘要和交付清单；专业导出配置、接收方兼容报告和文档健康报告；与 Git 的只读状态增强；只在选定资料范围内工作的可选 AI。

### 8.3 明确不做

实时多人协作、评论后台、复杂组织权限、全库自动 AI 问答、自建同步服务、移动端、Web 全功能版、插件市场、数据库/白板/日记/任务管理全家桶、通用 PDF/Office/OCR 资料库。

## 9. 分阶段战略路线图

时间按每周约 20 小时估计，日期可以延后，进入/退出条件不能跳过。

### 阶段 0：可信候选（现在至 4 周）

目标：让两位现有用户在真实机器上使用可安装、行为可解释的 Windows 候选版。

完成 smoke、typecheck、lint、test、build、a11y；解释并修复/优化搜索性能；两个隔离环境完成安装、启动、文件关联、保存、升级、卸载和用户文件保留；对齐 GitHub/Gitee 远端并运行真实候选 Draft；完成两位用户任务记录。

退出条件：不存在 P0 数据/发行阻断；用户能安装并打开自己的资料；更新、SM.MS 和拼写词典行为与隐私文档一致。

### 阶段 1：外部 Alpha（1–3 个月）

招募 6–8 位样本，至少一半不是熟人；提供脱敏示例和任务演示；做允许正常使用竞品的等价任务对照；按最大阻塞只做一个主要增量。

退出条件：多数样本独立完成“找到来源 -> 插入 -> 写作 -> 保存重开 -> 导出”；至少 3 人在第二个真实任务主动再次使用；没有内容损坏或不可解释的数据结果。

### 阶段 2：个人专业版与公开 Beta（3–6 个月）

围绕专业交付包、来源/断链/缺图/过期报告、项目模板、批量检查、1k/5k 文档库体验、8 小时运行和第二设备验证。建议至少 20 位激活用户进入四周观察，报告样本量和失访后的 W4 留存；至少 5 位非关联用户完成真实付款实验。

### 阶段 3：团队交付桥梁（6–12 个月，有条件）

进入条件是至少 3 个小团队重复提出同一类交付、评审或共同维护问题，且个人版已有稳定外部使用。先做责任人、评审状态、更新时间、变更摘要、健康报告、交付清单和现有平台共存；不先做实时协同和复杂 RBAC。

### 阶段 4：企业内部知识库（12 个月以后，有预算和团队后）

企业版需要身份、组织、SSO、RBAC、审计、保留策略、备份恢复、部署升级、监控、SLA、安全响应、评论/评审/通知和并发模型。只有出现付费团队、明确部署需求和专门维护能力后才评估服务端/同步架构。

## 10. 用户验证和指标体系

北极星指标：

> **每周使用既有资料完成并实际交付或继续维护一份文档成果的活跃用户数。**

启动次数、创建笔记数、图谱节点数、停留时长和 GitHub Star 只能作为诊断数据。

| 阶段 | 关键事件 | 记录方式 |
| --- | --- | --- |
| 安装 | 成功安装并打开自己的目录 | 平台、版本、首次错误和支持时间 |
| 激活 | 找到来源、插入引用、保存重开、导出 | 15 分钟独立完成率和提示次数 |
| 复用 | 旧资料进入新文档并保留来源 | 每周有效来源复用用户数/比例 |
| 交付 | 接收方能阅读和继续使用 | 缺图、断链、格式返工和失败原因 |
| 留存 | 下一周/第四周完成第二次任务 | 逐人记录 W1/W4，不在 2 人样本上夸大比例 |
| 商业 | 真实付款且继续使用 | 付款、退款、30 天使用和支持时间 |

两位现有用户连续两周每人至少 3 次任务，记录原工具、资料来源、阻塞、结果和下一次使用理由。研究重点是观察，不是让用户替产品设计功能。

## 11. 商业化顺序

不对读取、保存、恢复和取回自己的 Markdown 收费；不在重复价值成立前开发复杂账号、授权和支付后台；收费对象应是专业结果、批量维护、交付效率或团队治理。

| 阶段 | 实验 | 目的 |
| --- | --- | --- |
| 种子期 | 免费使用、维护赞助 | 判断是否有自然支持，不预测收入 |
| Alpha 后 | 99–199 元创始用户支持包/预购，人工交付 | 验证真实付款而非问卷意愿 |
| 个人专业版 | 免费核心 + 一次性许可或年度维护二选一 | 依据转化、退款和兼容成本决定模型 |
| 团队阶段 | 团队席位、交付治理和支持方案 | 只在团队治理能力存在后收费 |

首个付款实验至少需要 5 位非关联用户，记录退款、30 天使用和支持时间。个人 Pro 最可能的价值是专业导出配置、项目文档集合交付包、来源/断链/缺图/过期报告、模板和批量检查。

## 12. GitHub 外部发布与增长

GitHub 的首要作用是获得合格试用和问题反馈，而不是追求 Star。发布前必须实际核对源码主仓/镜像、`package.json` owner/repo、tag -> Draft、候选 commit、Windows 安装器和用户文件保留，并让 README、CHANGELOG、隐私、安全、已知限制和反馈模板与候选版本一致。

发布内容围绕一个任务：用旧排障记录写成带来源的技术说明；同时展示 Paperin 如何与 Obsidian、Typora、VS Code、语雀共存，而不是强迫用户迁出全部资料。

## 13. AI 主导开发治理

AI 是实现工具，不是用户代表、需求来源或发布责任人。固定流水线：

```text
真实任务/门禁失败 -> 明确用户行为和风险 -> 先写失败测试 -> 最小实现
-> 代码与进程边界复核 -> 全量门禁 -> Electron/安装态/真人验证
-> 文档与变更记录 -> 候选发布
```

同一时间只推进一个主产品结果；完成结论绑定当前 commit 和新鲜命令输出；文件、IPC、编辑器、导出和发行变更必须有真实链路验证；触及超过 450 行文件时先拆职责；每两周保留时段只做用户任务、安装、性能和失效入口清理；AI 不得自动调整性能阈值、静默忽略失败或生成虚构用户研究。

## 14. 主要风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 定位变宽 | 同时启动 AI、同步、数据库、团队、移动端 | 每阶段只保留一个核心用户结果 |
| 测试成熟错觉 | 测试全绿但性能、安装或真人任务失败 | 自动、桌面、安装和用户任务分开计分 |
| 性能债务 | 5000 篇搜索持续超阈值 | 拆时延并复现根因，不盲改阈值 |
| 数据不信任 | 静默覆盖、乱码、错误成功提示 | 文件安全 P0，保留恢复材料和用户选择 |
| 发行支持失控 | 多平台一起承诺 | 先 Windows 候选，平台逐个开放 |
| 同质化 | 文案只剩本地、Markdown、主题、图谱 | 始终表达“资料到可维护交付文档” |
| 商业化过早 | 先开发授权，没有重复用户 | 先人工付款实验 |
| 团队扩张过早 | 没有团队样本就做账号/RBAC | 3 个团队重复需求后再进入 |
| AI 维护膨胀 | 大文件、重复状态、警告增加 | 触及即拆、直接测试、全量门禁 |

## 15. 决策清单

已经确定：产品是本地 Markdown 项目知识工作台；第一用户是维护技术和项目文档的个人贡献者；当前是个人版私有种子验证；商业策略暂时免费；团队/企业只作为条件路线。

必须用证据决定：GitHub/Gitee 主渠道与镜像关系；搜索优化优先索引复用、增量更新还是缓存；个人 Pro 的一次性许可或年度维护；外部用户最看重来源复用、可靠保存还是专业交付；是否需要可选 AI。

当前否决：用功能数量追赶竞品；在性能、安装和真人任务未收敛时正式公开；以 2 位用户、测试数量、下载量或 Star 宣称 PMF；把共享目录称为实时团队协作或企业知识库。

## 16. 未来 30 天执行顺序

| 顺序 | 工作 | 完成证据 |
| ---: | --- | --- |
| 1 | 复现和定位 5000 篇搜索性能红灯 | 固定环境多轮结果、阶段耗时、根因和回归测试 |
| 2 | 完成 Windows 候选安装循环 | 两个隔离环境的安装/启动/关联/保存/升级/卸载/数据保留记录 |
| 3 | 对齐 GitHub/Gitee 远端与发布 owner/repo | 实际候选 Draft Release 与正确 commit 记录 |
| 4 | 两位用户各完成至少 3 次真实任务观察 | 逐人任务记录、阻塞、成果和再次使用理由 |
| 5 | 只修一个最大真实阻塞 | 用户前后任务对照与对应测试 |
| 6 | 降低警告噪声并建立包体/启动预算 | 真实冷启动和编辑体验数据 |
| 7 | 发布外部 Alpha 决策 | 通过/不通过清单；未通过则继续私有种子 |

30 天后的最大交付不应是新功能，而应是一个能被陌生用户安装的候选包、一份真实任务观察记录，以及能解释性能和发布风险的证据。

## 17. 最终判断

Paperin 当前最有价值的资产不是功能数量，而是三个已经组合起来的基础：普通本地文件、来源进入写作的闭环、较深入的数据可靠性工程。它们足以支撑一个有辨识度的个人产品，但尚未自动构成市场优势。

正确顺序是：

```text
可信的个人本地工作台
  -> 外部个人用户反复使用
  -> 专业交付形成付费价值
  -> 小团队的作者到团队交付桥梁
  -> 有预算和维护团队后再做企业治理
```

近期唯一值得追踪的成功标准是：

> **陌生目标用户不需要开发者在旁指导，就能用自己的资料完成一份带来源的真实文档，安全保存并交付，而且下一次还愿意继续使用。**
