# LastFileHome 项目评估与下一阶段产品方向

评估日期：2026-09-12（Asia/Shanghai）

代码基准：`671e989`，package 版本 `0.6.0`。

性质：当前代码的评估与产品建议；涉及实现状态时以 [REFACTOR-STATUS](REFACTOR-STATUS.md) 和 README 的验证结果为准。

## 1. 决策摘要

**保留现有技术路线和知识库工作区模型，停止横向扩充功能，先完成可靠性与界面收敛，再验证“资料复用到写作输出”的产品闭环。**

当前项目已经越过静态原型阶段：文件安全、文档会话、命令注册、上下文面板、索引和编辑器扩展都有真实实现与测试。重构的方向正确，也形成了可继续演进的基础。但“模块已拆分”“单元测试通过”和“用户能放心长期使用”之间仍有缺口，暂不适合把现状描述为完整重构完成或发布就绪。

下一步按以下顺序推进：

1. **恢复可信基线**：修复失效的 Electron smoke、收藏恢复、快捷键提示和文档计数，明确文件是否真正落盘。
2. **收口保存与会话**：证明大文档最后一次输入能被保存、关闭和导出正确承接，继续按职责拆分超限模块。
3. **完成界面第二轮收敛**：减少顶栏重复信息，增加路径定位，减轻大纲，统一窄窗口与可访问性。
4. **验证核心产品价值**：让已有笔记容易找到、容易重新利用，并稳定导出；先做搜索回访和输出质量，再判断 AI、发布站点等扩展。
5. **按证据发布**：先在 Windows 开发与安装环境采集证据，再完成其他目标平台门禁；平台未验证不能被“构建成功”替代。

- [实施计划与验收清单](NEXT-DEVELOPMENT-PLAN.md)：任务 ID、依赖、工作量、测试、发布与回退。

### 4.1 不应重复安排的已完成工作

- 顶栏已经从多条 chrome 合并为一条，下一步应减少横向拥挤，而非再次安排“合并四条顶栏”。
- 侧栏已存在搜索触发、最近编辑、收藏和底部入口；收藏的问题是恢复与完整性，不是缺少按钮。
- ContextDock、命令作用域、菜单灰显和低频对话框懒加载已存在。
- 九套主题及全局减少动态效果规则已存在；下一步是实际使用位置的可读性与交互验收。
- 文件关联、外部文件标签、版本历史、图谱、导出都有实现，不能以 demo 是否出现作为能力清单。

## 5. 发现清单：由事实推导下一步

### F01 / P0：当前真实 Electron 门禁失效【实测 + 代码确认】

`src/main/testing/electron-smoke.ts:109` 和 `:121` 仍读取 `.current-file-banner-title`，当前 CurrentFileBanner 已不渲染该元素。本次失败数据仍显示 `source: external`、`tabs: 2`，因此**不能把报错文字直接当作“系统关联产品功能坏了”**；可以确认的是测试契约已脱离界面。

影响：发布证据不可信，大文档性能流程的前置步骤也被阻断。修复方向：以活动标签、来源语义和正文内容联合断言；保留去重、路径授权与真实磁盘检查，不能为了变绿而删除断言。

### F02 / P1：收藏只有写入，没有重启加载【代码确认】

`app/useSidebarFavorites.ts:30–34` 从 `null` 初始化，仅调用写入型 `usePersistedSetting`。全库 `sidebarFavorites` 检索未发现 settings.get 或其他恢复接线。当前会话切换工作区可以保留内存分桶，但重启后的收藏不会被读回；重启后首次新收藏还可能用当前新建分桶替换已有持久化集合。

影响：用户认为收藏丢失，已有文档“收藏持久化完成”的表述过强。先补重挂载读取、加载前点击合并、多个工作区保留、损坏数据和读写失败测试；随后验证重命名/移动/删除对收藏引用的迁移。

### F03 / P1：快捷键提示与执行契约不一致【代码确认】

`SidebarQuickNav.tsx:76` 写死 `Ctrl K`；`data/shortcuts.ts:47` 默认快速打开为 `Ctrl+P`，`:54` 的 `Ctrl+K` 是插入链接。应由实际快捷键映射生成提示，并适配自定义键位与平台展示。优先保留既有绑定，避免修文案时制造编辑器快捷键冲突。

### F04 / P1：侧栏“文档数”统计了根节点【代码确认】

`Sidebar/index.tsx:260–261` 使用 `workspaceNodes.length`，而 `Sidebar/fileTree.ts` 的 `buildWorkspaceFileTree` 返回单元素根目录数组。这解释了截图中目录很多却显示“1 个文档”的现象。

应递归统计 Markdown 叶子文件，明确总数、当前筛选数、已索引数的区别；目录扫描截断时显示“已发现 N 篇，扫描未完整”，不能把索引预算或根目录数叫文档总数。

### F05 / P1：未落盘与已保存语义冲突【截图 + 代码确认】

截图中的来源条同时出现“知识库文件 / 未保存文档 / 已保存”。`CurrentFileBanner` 由路径缺失生成“未保存文档”，由 dirty=false 生成“已保存”；来源分类函数把无路径示例/未命名文档归入 workspace 体验，UI 又将这个来源直接翻译为“知识库文件”。

需要将**工作区归属、文档种类、磁盘持久化状态**分开表达。“未修改示例”不等于“已写入磁盘”。这既是文案问题，也是状态建模问题；不要只隐藏来源条掩盖它。

### F06 / P0 验证优先级：大文档缓存保存尚未证明末次输入安全【风险待验证】

`large-document-save.ts` 实际判断 `content.length > 1_000_000`，是 JavaScript 字符串长度，不是文档所述的“>1 MiB 字节数”。`useDocumentSaving` 和 `useDocumentSession.liveContentOf` 对大内容直接读缓存，而监听回调带防抖。

存在“最后输入尚未序列化进缓存，用户立即保存/关闭”的风险窗口；本次没有复现实际丢字，不将其列为已发生的数据丢失事故。两个阈值函数测试只能证明选用了缓存，不能证明缓存足够新。

下一步必须以编辑版本、快照版本和写盘确认建立契约，验证中文输入法提交、即时 Ctrl+S、立即关闭、切换标签及保存期间继续输入。优化目标同时包含正确性和响应时间，不能靠复用旧快照取得好看的延迟。

### F07 / P1：渲染阶段仍可能做无关全文序列化【代码确认路径，性能影响待测】

`AppComposition.tsx:456` 每次渲染给 AppDialogs 传 `liveContentOf(activeFileId)`。历史对话框虽然按需挂载，这个参数仍会先求值；普通文档分支会调用编辑器 `getMarkdown()`。

应采集 React/序列化耗时后，把历史快照获取移到打开或实际需要对比时；不要把内容再复制成第二套可独立修改的正文状态。此问题说明“分包完成”不等于“运行时开销收敛”。

### F08 / P1：低对比信息与现有门禁覆盖不等价【实测 + 截图】

43 项 token 组合依赖棘轮基线；`--text-3/--text-4` 只报告、不阻断，而路径、计数和保存状态正在使用这些 token。辅助信息仍可能是正常可读文字，不能仅因命名为“弱提示”就豁免。

对正文和有效控件文字按实际背景校验；对装饰分隔线、必要控件边界和焦点分别建 token。W3C 要求正常文字最低 4.5:1，但停用控件/纯装饰存在例外；非文字 3:1 面向识别控件与状态所必需的视觉信息，不能泛化为所有装饰边线都要 3:1。[文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)、[非文字对比度说明](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)。

### F09 / P1：CI 与发布身份仍是迁移缺口【代码确认 + 实测】

仓库保留校验 CI 的脚本，却未包含其目标 workflow。打包名称、appId、发布仓库与界面仍使用 MarkdownSoft 标识，而 README 使用 LastFileHome。不能直接全局替换 appId 或状态目录；现有 userData、`.markdownsoft` 工作区状态、文件关联、升级目标均可能受影响。

建议先统一对外名称与帮助内容，安装身份与存储路径通过独立 ADR 决定是否保留兼容。恢复 CI 时禁止顺带配置未经确认的自动发布。

### F10 / P2：文档完成度漂移【代码确认】

旧 demo 评估正文仍描述“没有收藏/四层顶栏”，兼容矩阵仍写七套主题，实时状态不同段落的测试数与文件行数也不同。这会让后续开发重复实现、遗漏缺陷或错误判断发布条件。

处理方式：保留历史审查作为历史，不继续维护多个相互竞争的完成度清单；当前状态集中在 REFACTOR-STATUS，计划条目通过证据链接转成完成。

## 6. 对当前截图的界面判断

### 值得保留

- 编辑区是视觉主体，未堆放常驻富文本工具栏；符合长期写作场景。
- 左侧知识库与右侧大纲构成明确的“找文件—写内容—看结构”布局。
- 低饱和绿调、浅色侧栏和留白已经形成较一致的气质。
- 标签与大纲具有可辨识层级；适合继续打磨，不需要重做整套皮肤。

### 下一轮最值得改的地方

| 区域 | 当前问题 | 改进方向 | 优先级 |
| --- | --- | --- | --- |
| 顶栏 | 品牌、五组菜单、库名、标签、来源/状态、第二个文件名、动作和窗口按钮并列 | 工作区归侧栏；文件名归标签；路径归正文上方；常态只保留少数文档动作 | P1 |
| 文件定位 | 看到文件名但不容易知道其目录位置；树里当前文件未明显呈现 | 面包屑 + 定位当前文件；来源与路径不再藏进细小胶囊 | P1 |
| 正文宽度 | 宽屏留白多，正文与两侧面板距离大；是否过窄受个人设置影响 | 提供舒适阅读/宽内容预设，保留用户设置；宽表格和代码局部横向滚动 | P2 |
| 大纲 | 每级标题都带字数、层级线和工具图标，视觉接近检查面板 | 默认仅标题与当前章节；统计放在选中项或明确开关内 | P2 |
| 文字层级 | 部分导航、统计和底部状态过小过淡 | 用间距、字号和位置做层级，避免依赖极低对比度 | P1 |
| 标题背景 | 截图 H1 背后有灰色条，可能为选中/光标态 | 先复查失焦和非选中态；若为默认样式再移除，不据截图误判 |
| 空状态 | 欢迎页介绍大量功能，新用户下一步不明确 | 新用户先打开知识库/新建笔记；示例独立且清楚标识 | P2 |
| 品牌 | LastFileHome 与 MarkdownSoft 两套称呼 | 对外名称统一；存储与升级身份另行兼容迁移 | P1 |

详细尺寸和交互见 [NEXT-UI-SPEC](NEXT-UI-SPEC.md)。所有尺寸是下一轮原型的建议初值，不是对截图的精确测量，也不能覆盖用户已有字体、宽度和行距设置。

## 7. 产品定位与竞争判断

建议的一句话定位：

> **面向中文写作者的本地 Markdown 知识工作台：已有资料容易找到，当前文章安心写完，内容能以文件形式长期保存和继续使用。**

“安静”应体现为少打断，“本地”应体现为可恢复与可迁出，“知识库”应体现为找得到和用得上；三者都需要行为证明。

### 7.1 初期用户与核心任务

| 人群 | 当前需求假设 | 产品首先解决的任务 |
| --- | --- | --- |
| 经常写技术笔记、学习总结的人 | 有 Markdown 文件夹，但查找和复用困难 | 从目录/搜索找到旧笔记，定位段落，继续编辑 |
| 长文、教程和知识内容作者 | 希望安静写作并保留本地原稿 | 持续写作、可靠保存、恢复历史、导出交付 |
| 已有本地 Markdown 库、希望降低配置成本的人 | 希望文件可直接使用 | 直接打开已有目录，说明兼容边界，避免自动改写原文件 |

前两个是优先招募对象；第三个是迁移验证样本。团队协作管理员、数据库搭建者、插件开发者不作为首阶段设计中心。这是资源排序，不代表判断这些人没有需求。

### 7.2 竞争事实与推论分开

本次只核查官方能力说明，不做市场规模、用户数量、付费转化率推断，也不沿用旧文档中的插件数与 Stars 数。

| 产品 | 官方已具备的能力 | 对 LastFileHome 的含义（产品推论） |
| --- | --- | --- |
| Obsidian | Markdown 文件为主要笔记格式；内置插件包含搜索、书签、反链、图谱、文件恢复等 | “纯 Markdown / 有反链 / 有恢复”不足以单独构成差异，需要更好的默认流程和输出体验 |
| Typora | 文件树/文件列表、大纲、统计、专注与打字机模式；支持多种导出，部分格式依赖 Pandoc | 不能把它描述成完全没有文件管理；优势需要落在知识库回访、一致状态和中文工作流的整体体验 |
| 思源 | 官方强调隐私优先、所见即所得、块级引用与双链 | 以文档/普通文件为中心是可理解的取舍；不应模仿块级数据库再承担新模型成本 |

资料：[Obsidian Markdown 文件](https://obsidian.md/help/import/markdown)、[Obsidian 内置插件](https://obsidian.md/help/plugins)、[Typora 官方功能](https://www.typora.io/)、[Typora 导出说明](https://support.typora.io/Export/)、[思源官网](https://b3log.org/siyuan/)。以上仅支持能力事实，**不能据此宣称某个市场位置无人占据或已证明有付费需求**。

### 7.3 应形成的核心闭环

```mermaid
flowchart LR
    A[打开已有知识库] --> B[找到相关文件与段落]
    B --> C[继续写作或引用旧笔记]
    C --> D[可靠保存与可恢复历史]
    D --> E[导出与实际使用]
    E --> B
```

下一个版本重点不是让五个阶段各增加一堆功能，而是让同一篇文章在这条路径中不丢上下文、不丢输入、不出现含糊状态。

## 8. 产品投资顺序与范围控制

| 方向 | 决策 | 交付边界 |
| --- | --- | --- |
| 保存/恢复/冲突 | 立即投入 | 先证明正确性，再优化速度；失败可操作、可保留内容 |
| 搜索与回访 | 下一阶段核心增量 | 文件快速打开与全文搜索语义清楚；排名、片段、回到原位置 |
| 写作体验 | 持续打磨 | 路径、主题可读性、轻大纲、输入法、焦点和版面预设 |
| 输出质量 | 搜索闭环后投入 | 先稳定现有 HTML/PDF/DOCX；格式兼容报告与失败解释优于新增格式数量 |
| 模板/写作回顾 | 先小规模验证 | 2–3 个高频模板；使用已有目标和统计，不建复杂任务系统 |
| 图谱 | 维护与按需加载 | 保留已有能力，先修导航与性能，不追加图谱编辑器 |
| AI | 条件性实验 | 用户主动选择内容、可预览差异与撤销；先验证一个辅助任务，再决定集成 |
| 数字花园/平台发布 | 延后实验 | 先可移植导出，验证需求后评估发布链路和持续维护成本 |
| 自建同步/协作/移动端/公开插件市场 | 本阶段不排期 | 需要独立产品与架构立项，不能作为现有重构的小附加项 |

AI 初次实验优先比较“选中段落生成有来源的整理建议”或“跨笔记检索定位”，不默认增加常驻聊天侧栏。BYOK/本地模型也不能代替权限设计；是否上传、发送范围和成本必须在用户实际执行时明确，输出先供审阅。

商业化暂不绑定具体价格或收入目标。先取得持续使用与付费意愿证据，再比较支持服务、付费扩展或其他模式；文件打开、保存、迁出和安全恢复不应成为阻断用户取回内容的筹码。

## 9. 用户验证和成功标准

这些是建议的实验门槛，**不是已有用户数据或统计显著结论**。

第一轮招募 6–8 名符合画像的用户，使用可公开或合成的知识库，完成：打开目录、找到指定旧笔记、输入中文并立即保存、关闭重开、找到此前段落、导出一份可交付文档。

| 问题 | 采集方式 | 初期决策门槛 |
| --- | --- | --- |
| 是否理解知识库与文件 | 观察首轮任务和口头解释 | 至少 6/8 无需解释即可完成打开与保存；不足则改引导 |
| 是否能快速找回资料 | 预设查找任务、记录耗时和路径 | 同一任务相对当前版中位耗时降低约 25%；小样本只判断方向 |
| 是否能相信保存状态 | 即时保存、冲突、恢复任务 | 所有验收样本均无静默覆盖/内容遗漏；任一异常先停止放量 |
| 是否能长期使用 | 10–20 人、两周试用与简短访谈 | 至少半数在第二周自然回访并完成写作或资料复用；否则回到任务定位 |
| 是否值得做 AI/同步/发布扩展 | 记录实际绕行和重复任务 | 同类问题被至少 3 名目标用户独立提出，并有具体任务证据再立项 |

不以内置按钮数量、编辑器打开时长、AI 生成字数作为北极星指标。优先看**每周完成一次“找回资料并形成有效编辑或输出”的用户数/比例**；早期可用自愿日志与访谈采集，不先建设遥测系统。

性能、状态与使用统计默认本地；诊断导出只含聚合数据且由用户检查。任何远程分析另行设计明确选择，不能上传笔记正文、标题、路径或搜索词来证明产品活跃。
