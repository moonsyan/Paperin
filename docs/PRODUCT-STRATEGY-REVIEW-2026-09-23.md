> 复审日期：2026-09-23（Asia/Shanghai）

## 1. 当前最重要的判断

**Paperin 已经拥有覆盖写作、个人知识管理和项目文档维护的产品基础；当前短板主要是可信度收敛、真实使用验证和对外表达的一致性。** 它不再是只有编辑器的演示原型，但仍不能把代码量、测试数量或一个 Release 当成成熟产品证明。

建议产品主定位调整为：

> **Paperin 是本地优先的 Markdown 写作与知识工作台，让文章、笔记和项目资料在同一个空间中持续积累、相互复用，并形成可维护、可交付的成果。**

面向用户的短表达可以是：**安心写作，让知识持续产生作品。** 面向项目资料场景的解释是：**从资料到成稿，从成稿到持续维护。** 这些是建议文案，本次没有直接修改应用入口。

用户明确希望兼顾三类场景，因此不能把整个产品永久缩成“写一段技术说明”。但早期推广仍需要一个有辨识度的示范任务：用自己的旧资料完成一篇文章或项目文档，保留来源，保存重开，检查并交付。通用写作和个人知识管理是持续使用的基础；资料复用、维护提醒与交付组合是优先验证的差异化。

当前阶段应描述为：

> **已有早期公开发行记录、正在打磨 0.7.0 的个人桌面产品；核心功能较齐备，仍处于种子使用与可靠性验证期。**

本次已核实 GitHub 公开存在 [v0.6.0 Release](https://github.com/moonsyan/Paperin/releases/tag/v0.6.0)，页面显示 9 项资产。因此“从未发布”和“GitHub 不可达”都不准确。公开页不能证明当前 0.7.0 已发布、安装成功、已有规模用户，也看不到私有 Draft；资产下载和安装未在本次验证。

近期优先级：

1. 修复本次复现的工作区状态目录越界和来源归属问题。
2. 恢复默认测试与性能门禁，收敛 Windows 安装、真实输入法和导出接收方证据。
3. 清理无效设置、弹窗焦点缺口和测试化首屏，让两位现有用户在三类任务中真实使用。
4. 通过外部小样本验证，再扩大发布与商业实验。
5. 团队、企业是条件成立后的扩展方向，不与个人版同时开工。

## 2. 决策前提与审查边界

| 事项 | 已知事实 | 对战略的约束 |
| --- | --- | --- |
| 产品范围 | 通用写作、技术/项目文档、个人知识管理都希望保留 | 共用一套文档、工作区、搜索和交付能力，避免形成三个模式 |
| 发展顺序 | 先个人自用，成熟后服务外部用户，再进入团队与企业内部知识库 | 以阶段证据解锁投入 |
| 开发方式 | 主要由 AI 完成，人工在晚上和周末投入 | 人工验收、需求判断和支持时间比产码速度更稀缺 |
| 用户 | 2 位真实用户 | 可发现问题，不能证明市场规模、留存或付费意愿 |
| 渠道 | GitHub；公开 v0.6.0 已可核验 | 应衔接已有用户升级路径，而非假定从零首次发行 |
| 收费 | 尚无明确计划 | 当前不需要先建设支付、账号和授权系统 |
| 工时与预算 | 没有精确每周工时、现金预算与运维安排 | 不沿用旧报告未经确认的“每周 20 小时”作为承诺 |
| 用户研究 | 仓库协议存在，正式任务记录仍未采集 | 研究表格不是研究结果；两位用户身份不再根据旧文档自行推定 |

“全量审查”在本次指覆盖全部主要产品域和工程边界：Main、Preload、Shared、Renderer、编辑器、工作区、搜索索引、引用、保存恢复、导出、设置、发布、测试和文档。对重点链路深入阅读和复现；不是逐行形式化证明，也不是已完成全平台渗透测试、八小时实测或所有竞品上手实验。

证据分为四类：**代码可见、自动检查/受控复现、真实环境与真人验证、战略假设**。下文不把这四类合并为一个“完成百分比”。

## 3. 产品现在具备什么

### 3.1 三条工作流应共用同一个产品

| 工作流 | 用户想完成的结果 | 当前实际能力 | 下一步应验证 |
| --- | --- | --- | --- |
| 通用写作 | 写好、改好、保存并输出文章 | Milkdown 编辑、GFM、表格、公式、Mermaid、脚注、frontmatter、大纲、专注/打字机、查找替换、统计、多格式输出 | 中文长时间输入、粘贴、撤销、复杂长文与排版是否顺手；不强迫每篇文章都有引用 |
| 个人知识管理 | 把积累的内容找回来，继续使用 | 本地目录、多标签、最近、收藏、标签、Wiki 链接、反链、图谱、全文/结构搜索和阅读位置恢复 | 是否找得到旧内容，是否在后续任务中用得上；图谱使用次数不代表知识价值 |
| 技术与项目文档 | 把资料变成可维护、可交付的说明 | 搜索/反链插入引用、按文档来源基线、复核、显式重定位、导出检查、集合 HTML、发布配置和交付报告 | 引用归属准确性、来源变化理解、真实接收方可读性以及维护返工是否减少 |

三条路径不是三个独立产品。文章可以先自由写作，之后引用知识库资料；项目文档交付后仍回到个人资料库继续积累。空白文档必须始终是合法起点。

当前入口仍突出“打开资料 → 用来源写一段技术说明”。六类模板确实存在：`document-collection.ts` 提供 README、API、设计、更新日志，`writing-templates.ts` 补充技术文章与决策记录；命令面板及文件命令已接线。它们整体偏项目文档，通用写作与个人知识整理的首屏引导仍有提升空间。不能只看某个模板文件就判断能力缺失。

### 3.3 必须公开解释的容量与语义边界

| 边界 | 当前代码值/行为 | 产品含义 |
| --- | --- | --- |
| 打开正文 | 最高 20 MiB | 能打开不等于全部知识功能覆盖该文件，也不代表该大小下体验已验收 |
| 索引与搜索 | 最多 5000 篇，单篇 2 MiB | 大库或大文件可能未完整覆盖；“没有搜到”必须结合覆盖状态解释 |
| 搜索正文语料 | 单根 64 MiB、主进程合计 128 MiB，按 UTF-8 路径/行内容计量 | 不等于总 RSS 上限，JS 对象和字符串有额外内存成本 |
| 历史快照 | 单文件最多 20 份、累计 5 MiB；正文超过 2 MiB 不记录 | 历史不是无限备份；与草稿、保存恢复材料是不同保护层 |
| 来源基线 | 最多 50 篇引用文档、每篇 20 条、总计 200 条 | 是有界辅助状态，不是全库完整的来源治理账本；超额裁剪后的可见性应验证 |
| 来源健康 | 相对路径 + mtime，支持当前/变化/缺失/未验证 | 表示维护提醒，不是内容校验、引用片段差异或结论正确性认证 |
| 发布配置 | 最多 20 条 | 已有轻量复用能力，尚非企业发布策略 |
| 集合导出 | 公式/Mermaid 可降级为源码表达 | 不得以单篇 DOM 导出效果承诺集合完全一致 |
| EPUB/LaTeX 等 | 经用户环境中的 Pandoc | 是条件能力，不是开箱即用的所有格式保证 |

Markdown 正文和附件可直接取回，但来源复核记录、布局、搜索记录等在 `.paperin` 或应用数据中。**正文可迁移与所有知识状态可迁移必须分开承诺。** 企业扩展前，还需区分个人偏好、可共享元数据和需审计的组织记录。

| 层次 | 当前判断 | 尚缺什么 |

### 4.2 新发现问题改变近期优先级

以下不是重复旧报告待办，已按当前代码重新判断：

| 编号 | 证据 | 问题与影响 | 建议优先级 |
| --- | --- | --- | --- |
| A01 | 隔离合成文件系统已复现 | `.paperin` 为 junction 时，状态 store 可读写工作区外固定 JSON 状态文件；未复用正常文件路径的真实路径授权 | P0，外部候选前处理 |
| A02 | Hook 测试 + 调用链已复现/确认 | 草稿或已保存库外文章 A 登记来源后切换到库内 B，来源可能被归给 B；库外文章来源也无法持久化 | P1，来源功能可信度阻断 |
| A03 | Hook 测试已复现 | 插入来源的 stat 晚于首次保存返回，基线留在旧草稿身份，不能正确持久归属 | P1，与 A02 同一身份生命周期治理 |
| A08 | 生产调用链确认 | 应用内改名/移动没有调用已有来源路径重映射；引用文章或来源文件改路径后基线失真 | P1，与 A02/A03 一并修复和回归 |
| A04 | 静态确认，未注入故障 | watcher 启动失败静默降级，运行时 error 未接入；命中语料不重新 stat，存在检索新鲜度风险 | P1，需故障测试判定可见行为 |
| A05 | 代码与配置确认 | 日志直接写 Error.message/stack；安装脚本 live 分支仅调用旧版安装，升级/卸载等仍为骨架；安装 job 禁用且正式发布不校验安装证据 | P1，补实现与隐私/发行闭环 |
| A10 | 全量与独立重跑 | 默认测试因安装脚本 shebang 转换失败；watcher 稳定 P95 两次约 9.7–9.9 秒，合成性能三项超阈值 | P1，恢复工程门禁并完成性能 profiling |
| A06 | 静态确认 | 主编排 771 行，含重定位状态和异步处理；8 个生产文件超过 450 行 | P1/P2，修复相关职责时拆分，避免继续膨胀 |
| A07 | 调用链/文案核对 | 资源包未走普通格式的统一预检入口；来源能力、性能阶段与多处文档不一致 | P2，契约对齐与文档治理 |
| A09 | 生产调用链与首屏观察 | 拼写检查设置对正文无效；部分弹窗无统一焦点闭环；首次体验暴露 `R11_SYNTH_*` 测试标记 | P2，按用户可见契约逐项收敛 |

定向缺陷复现与既有全量测试分别报告。既有测试即使全部通过，也不会抵消新增反例。报告提出修复优先级，本次没有擅自修改产品代码。

## 5. 竞争格局：实际在与什么竞争

核查口径：2026-09-23 官方公开资料；不是所有软件的实机横评。不使用市场份额、虚构用户量或未经同条件测试的性能排名。表中“机会”均为战略推断。

### 5.1 用户点名的五个产品

| 产品 | 可核验的成熟能力与模式 | Paperin 的竞争关系与机会 |
| --- | --- | --- |
| **Obsidian** | 本地 Markdown、链接/图谱、Canvas、插件、Sync/Publish；应用和商用使用免费，商用许可已是自愿支持。[官方产品](https://obsidian.md/)、[定价](https://obsidian.md/pricing) | 同时争夺个人知识库与写作用户。本地、免费商用、双链和图谱不是独有优势；应验证在既有资料中完成写作、维护与交付需要多少步骤和配置 |
| **思源笔记** | 块编辑/引用、双链、SQL/数据库、PDF 批注、API/集市；原始文档为 `.sy` JSON，可导出 Markdown 与资源等格式。本地功能免费，另有同步/云服务方案。[官方仓库](https://github.com/siyuan-note/siyuan)、[方案](https://b3log.org/siyuan/en/pricing.html) | 对结构化知识组织更有积累。Paperin 可突出直接维护现有 `.md` 项目目录的便利，不应称思源不开放或无法迁移；也不必为追赶块数据库改变正文模型 |
| **语雀** | 个人结构化知识库与团队在线知识沉淀、协作、分享是主要方向。[团队产品](https://www.yuque.com/about/groups) | 组织协作和面向读者的知识库体验是未来对标。近期优先让个人成稿容易交付到既有平台。价格页与部分帮助页本次未取得完整正文，价格、导出权益和权限粒度不下结论 |
| **Typora** | 原生文件、即时渲染、文件管理、搜索、专注写作；原生 PDF/HTML 等导出，Word/EPUB 等使用 Pandoc；一次购买，官网当前标价 US$14.99（未税），最多 3 台个人设备。[官网](https://typora.io/)、[导出说明](https://support.typora.io/Export/)、[授权](https://support.typora.io/purchase/) | 是单篇编辑手感的直接标杆。Paperin 必须先把输入、粘贴、撤销和长文写作做好；可以用跨文档复用与维护解释增加工作区复杂度的收益 |
| **MarkText** | MIT 开源、实时预览、CommonMark/GFM、源码/聚焦/打字机模式、HTML/PDF 导出。[官方仓库](https://github.com/marktext/marktext) | 免费开源编辑器竞争已存在。本次可见 [v0.19.1](https://github.com/marktext/marktext/releases/tag/v0.19.1) 及 [v0.20.0-rc.5 预发布](https://github.com/marktext/marktext/releases/tag/v0.20.0-rc.5)，不能再以“多年停更”支撑市场机会 |

Obsidian 的 [2026-09-15 变更记录](https://obsidian.md/changelog/)还列出 Desktop 1.14.2 **Catalyst 预览**的库外文件打开能力。单文件和知识库统一体验可以是 Paperin 的设计原则，不能声称竞品做不到；预览能力也不能直接写成所有稳定版已支持。

### 5.2 不能忽略的替代品

| 产品/组合 | 官方证据 | 战略启发 |
| --- | --- | --- |
| **Joplin** | 本地 SQLite 笔记模型、Markdown/JEX 导入导出、插件、Cloud/Teams/Server。[架构](https://joplinapp.org/help/dev/spec/architecture/)、[导出](https://joplinapp.org/help/apps/import_export/)、[方案](https://joplinapp.org/plans/) | 跨端同步与服务收费已是成熟产品路线；Paperin 的直接文件工作区与之不同，但不代表数据更开放或价值更高 |
| **Logseq** | 当前需区分 OG 文件图谱与 DB 版；DB 使用 SQLite，官方有 2.0 DB Beta。[版本差异](https://github.com/logseq/docs/blob/master/db-version-changes.md)、[发布](https://github.com/logseq/logseq/releases) | 大纲/节点知识系统与长文工作台存在不同取舍；不要把新旧版本功能混为一谈，也不要轻率跟进数据库迁移 |
| **Notion** | 页面/数据库/团队工作区，支持导出；桌面和移动端已有按页离线，包含子页和数据库范围限制。[离线](https://www.notion.com/en-gb/help/use-pages-offline)、[导出](https://www.notion.com/help/workspace-settings)、[方案](https://www.notion.com/pricing) | “云端无法离线”已是错误对比。Paperin 应解释无需账号、直接使用本地源文件的工作方式；不能以一个离线标签否定 Notion 的协作与组织能力 |
| **Zettlr** | 自由开源写作工作台，整合文献管理器、Pandoc、项目与发布配置。[官网](https://www.zettlr.com/) | 它与“从资料到作品”的方向相当接近，不只属于遥远的学术工具。Paperin 需要用中文项目资料与维护工作流证明差别，而非宣称首次连接知识与写作 |
| **VS Code + Git/扩展** | 官方 Markdown 支持已含预览、链接校验、查找引用、重命名更新链接。[Markdown 文档](https://code.visualstudio.com/docs/languages/markdown) | 很多目标用户已有此组合。对比时保留用户原有配置；用作者体验与任务完成成本竞争，不能把断链检查称为独家 |
| **Outline** | 团队协同、评论、角色权限、SSO、API，支持知识库导出，有托管和自托管方案。[产品](https://www.getoutline.com/)、[导出](https://docs.getoutline.com/s/guide/doc/export-Da6C7HqL8M)、[许可](https://docs.getoutline.com/s/hosting/doc/license-restrictions-f9aq6uEL3H) | 团队产品的门槛包括管理与运营；自托管也不等于无约束的开源商业授权，未来选型必须核对具体许可 |
| **Confluence** | 实时编辑、评论、通知、版本、权限、组织集成和分层企业服务。[官方功能](https://www.atlassian.com/software/confluence/features) | 企业采购关注组织治理、可靠运维、集成和责任，编辑器只是其中一层 |
| **GitBook** | 官方围绕文档知识、面向读者的发布和知识服务组织产品。[官网](https://www.gitbook.com/) | 发布以后如何被阅读、检索和维护同样有价值；本地交付是 Paperin 近期可做的起点，托管服务则是另一项持续成本 |

### 5.3 三种战略选择

| 选择 | 收益 | 代价 | 当前建议 |
| --- | --- | --- | --- |
| 极简 Markdown 编辑器 | 容易理解，适合单篇文章 | 与 Typora、MarkText 等直接同质竞争，已有知识能力价值被压缩 | 保留简洁体验，但不作为完整定位 |
| 全能个人知识系统 | 场景广、功能想象空间大 | 易同时扩张数据库、白板、移动、同步、插件；维护面超过业余资源 | 不作为近期建设路线 |
| **写作与知识相互复用的本地工作台** | 三类目标场景共享基础；能利用已有引用、维护、交付实现 | 需要把多步工作流做得易懂可靠，并证明用户获益 | **推荐主线** |

最重要的竞争对象是用户的现有工作方式：文件夹 + 搜索 + 编辑器 + 云文档，或者 Obsidian + 插件 + Pandoc。不能只与竞品“空白安装”比较，再要求用户为 Paperin 更换全部工具。

## 6. 如何强化定位与优势

### 6.1 品类、范围和切入口分开表达

- **品类**：本地 Markdown 写作与知识工作台。
- **范围**：文章写作、个人知识积累、项目资料维护。
- **首批可演示任务**：从旧资料完成一篇有来源、可继续维护的成果。
- **首批推广人群**：已经使用本地 Markdown，定期写文章或维护项目说明的个人作者、开发者和知识工作者。
- **扩展人群**：需要把个人成果交给同事、客户或组织知识库的文档责任人。

这让“通用”体现在文档和任务的普适性，而不是现在建设所有类型的知识工具。

### 6.2 哪些是基础，哪些可能成为优势

| 能力 | 今天的性质 | 怎样才成为用户优势 |
| --- | --- | --- |
| 本地 Markdown、离线核心、主题、双链/图谱 | 基础竞争条件，多家已有 | 迁入迁出损失小，打开自己的目录无需额外维护 |
| 编辑/保存/恢复工程 | 信任基础 | 真机、故障和长期使用结果稳定；不能由代码自证“最安全” |
| 搜索到引用，再到来源维护 | 差异化候选 | 用户少复制错内容、少丢来源，下一次更新能更快发现需复核处 |
| 集合输出、预检、发布配置、交付报告 | 差异化候选 | 接收方可读，输出稳定，减少漏图/断链及重新排版 |
| 三类任务共享工作区 | 产品结构优势候选 | 自由写作不被强制流程打断，知识管理又确实能帮助后续成果 |

护城河不会来自几个按钮。更可积累的资产是：真实任务样本、兼容与恢复夹具、可靠的发布质量、解释清楚的文档状态、长期用户信任，以及与现有工具共同工作的习惯。维护提醒的正确性比更多图谱样式更接近这条主线。

### 6.3 三条上手任务建议

| 入口 | 首个小成果 | 可用现有能力 | 建议后续改动 |
| --- | --- | --- | --- |
| 写一篇文章 | 新建并保存一篇短文，完成一次输出 | 空白文档、大纲、编辑、导出 | 通用示例与准确模板说明；不要求先学双链 |
| 整理一个项目 | 从已有资料写成一篇说明并保留出处 | 搜索、插入引用、来源健康、发布 | 提高引用与维护状态的可发现性，优先修复身份缺陷 |
| 继续使用知识库 | 找回一篇旧笔记，并在新的真实任务中用上 | 最近、收藏、标签、搜索、反链 | 观察找回路径；没有需求证据前不加复杂信息结构 |

本次建议不要求新建三套主页或三种应用模式。可以先用入门示例、命令入口与文案测试验证理解，再决定 UI 变化。

## 7. 分阶段发展路线

阶段以退出条件推进，时间窗仅用于安排。个人自用阶段允许保留其他工具作为工作习惯；可信后再逐步扩大默认使用场景。

| 阶段 | 要取得的结果 | 进入与退出依据 | 本阶段暂不承担 |
| --- | --- | --- | --- |
| **A：个人可依赖** | 两位现有用户用自己的资料完成真实工作 | 新发现路径/来源缺陷修复；Windows 安装与更新验证；两人各至少 3 次真实任务，三类场景均有观察机会；严重阻塞有结论 | 账号、云同步、企业服务 |
| **B：外部 Alpha** | 陌生目标用户无需开发者陪同也能完成任务并再次使用 | 依现有协议招募 6–8 人，至少半数非熟人；多数独立完成，至少 3 人在第二个真实任务主动使用；失败/受助保留记录 | 用下载量和 Star 宣称需求成立 |
| **C：个人公开 Beta** | 在确认的场景和平台形成稳定承诺 | 对所承诺场景完成独立任务确认、接收方矩阵与两设备八小时稳定性；资料复用提效主张按 12 人 U01/U02 验证；已知限制准确 | 为“全平台”口号降低验证范围 |
| **D：可持续个人产品** | 重复价值与支持成本可解释 | 两批各至少 20 名激活用户的成熟 W2/W4 观察；之后进行小规模真实付款实验 | 默认承诺永久更新、无限支持 |
| **E：团队交付桥梁** | 同一种个人成果能稳定进入团队工作流程 | 至少 3 个团队在两个周期重复同类需求，存在明确使用者、责任人和购买者 | 立即建设实时协作全家桶 |
| **F：企业内部知识库** | 组织知识可受控共享、治理与运维 | 有明确试点组织、责任人、重复需求、维护能力及预算，再评审服务端/同步模型；收费企业方案另外验证购买方 | 以本地 JSON + 共享盘冒充企业平台 |

资料复用切入口的 U01/U02、留存和商业指标定义参考[战略验收协议](development/strategy-validation.md)，能力状态以本次审查为准。这些人数与阈值是该主张的内部确认标准，不是行业标准，也不覆盖全部产品用户。通用写作、知识找回分别定义任务成功并记录分母，不因用户没有插入引用或导出就排除其价值。招募按实际能力分轮进行；样本不足时不得宣称提效或商业验证成立，但不自动禁止在安全、安装和已声明能力验证通过后开展限定范围的公开试用。团队/企业内部试点可以先于收费，工程安全门禁不因试点而降低。

### 7.1 接下来 30 天的具体安排

| 顺序 | 工作包 | 可验收交付 | 人工职责 |
| --- | --- | --- | --- |
| 1 | 路径安全 A01；来源身份与路径 A02/A03/A08 | 失败用例转绿，相关安全/会话回归；复测库外文件、草稿、首次保存、切标签、改名/移动与重开 | 核对用户实际看到的文章、来源和路径一致 |
| 2 | 工程门禁 A10；监听降级 A04 | 默认测试恢复；性能先 profiling 再优化且不放宽阈值；监听故障注入后状态可解释 | 在固定空闲环境复核同一候选，不用一次偶然绿灯放行 |
| 3 | 日志、安装与发布证据 A05 | 日志脱敏；补齐安装脚本的升级/卸载/关联/数据保留流程，再绑定正式发行 | 两个隔离环境验收同一候选 |
| 4 | 三类任务与可见契约 A09 | 每人至少 3 个真实任务；拼写开关、弹窗焦点和首次体验文案行为一致 | 选择真实任务、观察、判断结果是否有用 |
| 5 | 导出与输入体验收敛 | 常用中文输入、缩放与实际 PDF/HTML/DOCX 阅读器检查；普通/集合/资源包预检和降级说明准确 | 查看排版、字体、缺图和阅读效果 |
| 6 | 事实同步与外部 Alpha 决策 | README、入门、状态、容量限制及候选发布说明一致；形成一页放行/继续打磨结论 | 选择实际承诺范围、支持窗口和招募渠道 |

若工时不足，顺延 4–6，先保住 1–3；不通过加班和扩张功能掩盖未完成的验证。本轮性能已经重复红灯，应先 profiling 判断环境 I/O 与生产路径各自占比，再决定独立性能工作包，不照抄历史结论，也不放宽阈值。

### 7.2 个人阶段的投入比例建议

建议以实际每周可用时间为总量：约 40% 修复与实现、30% 真机和真实任务验证、20% 发布/文档/支持、10% 复盘。比例是资源约束工具，不是考勤要求。每轮同时只推进一个产品结果，另保留紧急数据问题通道。

AI 可以完成测试、实现、静态审查和文档草稿；产品负责人仍需选择问题、核验真人反馈、检查安装和成品、承担发布判断。继续提高产码速度不能自动填补这些缺口。

## 8. 团队与企业怎样逐步扩展

团队方向不必一开始就替换语雀、Notion、Confluence。推荐按三步演进：

1. **作者到团队的交付**：标准 Markdown/HTML/PDF、附件清单、明确降级、可读变更摘要。先减少团队接收成果的摩擦。
2. **小团队共同维护**：确认到底需要评审、责任人、发布状态还是多人同写；选择一个重复问题。将个人偏好与共享元数据分离，定义稳定文档身份、版本与冲突语义。
3. **组织知识治理**：再评审账号/租户、权限、审计、身份接入、备份恢复、部署升级、通知和运营控制面。

| 需要补的层 | 当前差距 | 进入企业前的要求 |
| --- | --- | --- |
| 文档身份与并发 | 目前以本地路径、窗口、进程锁和工作区 JSON 为中心 | 路径变化之外的稳定身份；跨设备冲突/合并规则；离线更新可解释 |
| 访问控制 | 没有组织权限主体 | 身份、成员/组、权限继承与撤销、分享范围；UI 隐藏不能替代服务端鉴权 |
| 协作流程 | 无评论审批和团队任务系统 | 谁负责、谁确认、当前发布版本是什么，以及通知规则 |
| 审计与数据治理 | 本地诊断与交付报告不是组织审计账本 | 可靠审计、保留/删除策略、备份恢复演练、敏感信息处理 |
| 运维与支持 | 晚间周末维护 | 可持续的更新、监控、安全响应、支持窗口和部署成本 |
| 内容存储 | 普通 Markdown + 私有应用状态 | 明确正文源、共享元数据、权限数据与派生索引的归属；保留可取回性 |

当前不建议预先建设 CRDT、租户服务或自建同步。未来选择文件/Git 协作、中心服务或实时编辑，需要依据实际并发任务和部署要求；不能只因为远期有企业愿景就现在重写桌面架构。

## 9. 商业化：先识别可付费结果

当前建议保持个人核心免费，先把下载、安装、任务完成和再次使用跑通。原有 MIT 代码和已公开能力应有稳定预期；不能将已经存在的导出功能简单重新命名为“未来 Pro”来假定收入。下列扩展收费候选指新增且经过验证的增量成果或维护服务，不把现有预检、集合发布、六类模板再算成未来新能力；付费分发也不能以限制已有 MIT 代码使用作为价值基础。

| 方式 | 合适时机 | 用户实际购买什么 | 主要成本 |
| --- | --- | --- | --- |
| 自愿赞助 | 现在即可作为可选支持方式评估 | 支持项目持续维护 | 收入不确定，不能视作需求验证 |
| 专业交付扩展/服务 | 重复用户明确需要更省事的专业成果后 | 已验证的批量检查、特定交付模板、长期兼容支持或服务 | 模板维护、格式兼容、售后时间 |
| 一次性付费发行/版本服务 | 个人用户愿付且升级边界明确后 | 便利分发、明确范围的专业能力与维护 | 许可边界、支付/退款、升级承诺 |
| 托管发布或同步订阅 | 明确持续需求与运维能力后 | 可持续的远程服务 | 存储、流量、备份、安全响应、可靠性支持 |
| 团队/企业方案 | 重复团队需求和付费伙伴形成后 | 权限、治理、部署、迁移与支持 | 长销售周期、集成、运维责任与客户定制 |

首个商业实验无需自建支付后台，也不先承诺某个固定价格。依据访谈中的实际成果形成清晰报价；至少 5 位非关联用户实际付款，观察 30 天退款、继续使用和交付支持时间。付费意向、赞赏、GitHub Star 都单独记录。

内部核算至少包括：

`可持续贡献 = 实收金额 − 退款 − 渠道/服务成本 − 按统一内部标准折算的交付与支持工时`

未明确续费、留存和服务成本前，不估算长期 LTV，不按“Markdown 用户很多”推算收入。将某项扩展做成收费模块、服务或开放能力，是以后需要单独确认的产品与许可决策。

## 10. 用户验证、增长与指标

### 10.1 两层价值指标

产品层观察：**每周用 Paperin 完成一项自己实际采用的写作、整理或维护成果的用户数**，按三类任务分别记录。

差异化验证继续沿用现有研究北极星：**已有资料通过有效复用进入真实成果，并已交付或继续维护的用户数**。前者描述完整产品范围，后者检验“知识促进成果”的定位。两者不可互换，不能以纯打开/收藏动作伪造复用。

两位用户阶段只报告“谁完成了哪类任务、遇到什么问题、是否主动再用”，不将 1/2 包装成有代表性的 50% 留存。

### 10.2 研究方法

- 三类任务先记录实际频率和原工具，再安排观察；用户说“三者都希望有”是产品意图，不等于三个场景都已有高频使用。
- 用可恢复副本；记录任务类型、版本、库规模区间、耗时、求助、失败、成果用途，不收集正文、真实路径和可识别个人信息。
- 对比用户常用工具的正常配置与插件，交叉操作顺序，避免熟悉度和记忆偏差。
- 首次完成与长期使用分开；保存成功、内容正确、接收方可读分别核验。
- W2 为激活后 day 7–13，W4 为 day 21–27；各批等待窗口成熟，保留失败、失访及撤回口径。
- 现有 12 人确认、两批 20 人队列等门槛是阶段决策工具；样本小仍需报告整数和不确定性，不能宣称普遍领先。

### 10.3 GitHub 与外部增长

先完成“一个清楚的承诺 + 一个可安装候选 + 一段真实任务演示 + 已知限制 + 可用反馈入口”。公开仓库目前仍以“开源 markdown 编辑器”概括产品，不能充分解释已有知识工作流价值；建议与本报告的主定位统一，但本次没有修改远端设置。[公开仓库](https://github.com/moonsyan/Paperin)

内容可以轮流展示三类任务：写文章、整理项目资料、从旧笔记产生新成果。首次招募仍围绕最清晰的一类重复任务，避免在同一轮用完全不同用户的反馈相互抵消。发布前写明当前版本、平台、升级路径、数据位置及实际验证范围。

先用 GitHub Release、Issues/讨论和目标用户的自愿试用收集反馈，不投放大范围获客。渠道指标看“安装 → 激活 → 再次真实使用”，Star 和下载仅是兴趣信号。同步保留现有工具共存路径，降低“迁移全部知识库”的心理成本。

## 11. 技术与 AI 开发治理

保留 Electron、React、TypeScript 与 Milkdown 的总体路线，当前没有证据支持框架重写。优先修复已有职责边界与用户可观察错误。

本次统计 `src/` 中非 `.test/.perf` 的 TS/TSX 共 370 个文件、50,391 行（含注释、空行和合成开发夹具；不是纯业务代码量），38 个超过 300 行、8 个超过 450 行。尤其 `AppComposition.tsx` 已达 771 行；状态页已同步同一行数表。规模数据用于识别维护成本，不能充当产品成熟度指标。

建议落实以下治理：

1. 每次变更只绑定一个用户结果或一个风险；AI 完成摘要必须指向具体代码、测试和环境。
2. 来源生命周期修复同时拆出身份迁移、重定位和视图编排，保持正文编辑器为状态源。
3. 单测绿色不覆盖缺失场景；草稿/保存/切标签、工作区路径变更、监听失败、导出接收方应使用行为测试。
4. CI 与本地门禁对齐；性能不放宽阈值，失败不被重跑中的一次成功掩盖；发布必须绑定经过安装验收的同一候选。
5. 依赖治理覆盖实际分发物。React、Milkdown、Mermaid 等在 `devDependencies` 但会被打入 Renderer，`npm audit --omit=dev` 为零不能证明全部产品依赖无告警。
6. 文档坚持一个当前状态入口；历史审查冻结，当前能力从代码重核。此轮发现多处“代码已实现、文档仍待办”的漂移，不继续复制状态表扩大同步负担。
7. 当前不要新增通用远程 AI 问答。若研究证明选择资料后生成大纲/摘要有重复价值，先限制在用户明确选择范围，保留来源、撤销、预览和无模型可用的完整工作流。

## 12. 决策与停止条件

| 情况 | 应采取的决定 |
| --- | --- |
| 再次发现越界写入、错误归属、静默损坏 | 停止相关功能扩张与发行，先做失败复现和修复 |
| 连续两轮只改最大阻塞，用户仍无改善或不愿再次使用 | 重新审视切入口/人群，收缩投入；不默认追加功能 |
| 用户主要只写单篇文章 | 提高编辑可靠性与简洁度，用观察决定知识能力如何收起 |
| 用户经常整理旧资料但不交付 | 优先找回、关联和维护体验，不强迫完成导出漏斗 |
| 用户反复为项目成果返工 | 优先来源维护、兼容和交付，验证专业付费结果 |
| 有团队询问，但没有重复任务与责任人 | 记录需求，保持标准文件交付；暂不建设组织后台 |
| 维护与支持长期挤占真实使用验证 | 限制平台和版本范围，减少并行功能 |

报告建议的核心取舍是：**范围上保留通用写作、个人知识与项目文档；建设上共用一套本地工作台；竞争上验证资料复用、维护和交付的组合价值；发展上先个人可靠，再外部采用，最后组织治理。**

下一阶段最值得获得的证据，是两位用户真的把它用于三类工作中的具体成果，以及陌生用户愿意在第二个真实任务继续使用。新的按钮、更多代码和更长的战略文档，都不能替代这个结果。
