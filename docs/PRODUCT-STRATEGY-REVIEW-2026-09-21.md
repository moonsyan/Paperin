## 1. 执行摘要

### 1.1 当前阶段

Paperin 已经不是界面原型，也不是只具备编辑器壳层的早期 Demo。当前代码形成了完整的 Electron 本地桌面架构，包含 Markdown 编辑、工作区、多标签、搜索、标签、反向链接、图谱、来源引用、草稿、版本历史、冲突保护、恢复写入和多格式导出，并有较密集的自动测试。

但 Paperin 仍不属于可稳定面向公众承诺的成熟产品。最准确的阶段定义是：

> **工程化程度较高的个人产品候选，正处于私有种子验证和发行门禁收敛期。**

判断依据如下：

- 当前 `lint`、TypeScript、全量测试和生产构建通过。
- 全量测试为 212 个文件、1549 项测试全部通过。
- 真实 Electron 冒烟当前失败，新建文档返回 `INVALID_TARGET`。
- 5000 篇合成库性能回归连续两次失败；Node 22 与 Node 24 均可复现。
- 生产性能套件 2 个文件中 1 个失败，搜索 IPC 同样返回 `INVALID_TARGET`。
- 生产依赖审计存在 1 个高危 `js-yaml` CPU 消耗漏洞。
- Windows 安装、升级、卸载，macOS/Linux 安装与签名仍未形成验证证据。
- 只有 2 位已知用户，真实任务记录、外部采用、留存和付费均未验证。

因此，下一阶段的核心目标不是继续增加功能，而是把“开发态功能丰富”转化为“可安装、可托付、可独立完成任务、可持续使用”的个人产品。

### 1.2 建议定位

推荐的正式定位是：

> **Paperin 是面向个人技术写作者和独立开发者的本地 Markdown 项目知识工作台，帮助用户把散落的项目资料写成带来源、可持续维护、可直接交付的文档。**

推荐短表达：

> **把项目资料，写成能交付、能继续维护的文档。**

这比“通用 Markdown 编辑器”更有识别度，也比“全能知识库”更符合当前资源。它能够自然覆盖用户已经确认的通用写作、技术文档、项目资料扩展和知识库管理，但用一个共同任务收敛这些场景：

```text
打开自己的资料
  -> 找到相关内容和来源
  -> 写成当前结论
  -> 安全保存并继续维护
  -> 交付 Markdown / HTML / PDF / Word 等成果
```

### 1.3 战略总纲

Paperin 应采用“窄定位、宽兼容、分阶段扩张”的路线：

1. 先把 Windows 个人版做成可信的外部测试产品。
2. 再验证个人技术写作与项目文档维护的重复价值。
3. 有重复使用后，围绕专业交付和维护效率验证个人付费。
4. 有至少 3 个小团队重复提出同一交付/评审问题后，再进入团队桥接能力。
5. 只有出现明确预算、专门维护能力和治理需求后，才建设企业权限、审计、部署与服务体系。

同步、全库 AI 问答、插件市场、移动端、实时协作、通用 PDF/Office 资料库，不应进入当前主线。

## 2. 已知资源与约束

| 项目 | 当前事实 | 对战略的影响 |
| --- | --- | --- |

## 3. 代码与工程现状

### 3.1 规模与边界

当前仓库 `src` 下有 573 个受版本管理文件、538 个 TypeScript 文件；排除 `.test` 与 `.perf` 后有 330 个生产 TypeScript 文件、约 41,845 行。29 个生产文件超过 300 行，4 个超过项目规定的 450 行上限：

| 文件 | 行数 | 主要风险 |
| --- | ---: | --- |
| `src/renderer/src/lib/docx.ts` | 559 | OOXML、关系、图片、样式与转换逻辑集中，专业导出继续扩展时回归面大 |
| `src/renderer/src/app/useAppSettings.ts` | 489 | 设置加载、状态和持久化装配集中 |
| `src/renderer/src/components/Editor/overlays/useEditorOverlays.ts` | 460 | 多类编辑器浮层与交互生命周期集中 |
| `src/renderer/src/components/Editor/instance/useMilkdownInstance.ts` | 456 | 编辑器插件注册和实例生命周期集中 |

这些文件不是立即整仓重构的理由，但触及对应功能时必须先拆职责并补直接测试。AI 主导开发尤其需要控制单文件复杂度，否则“生成速度”会迅速转化为审查和回归成本。

### 3.2 架构判断

当前架构边界总体健康：

```text
Renderer (React / Milkdown)
  -> window.desktopAPI
Preload (contextBridge + typed narrow API)
  -> named IPC channels
Main (文件、工作区、索引、窗口、设置、历史、导出)
Shared (DTO、状态、常量、纯逻辑)
```

核对结果：

- 生产 Renderer 未发现直接导入 Electron 或 Node 文件系统；命中的 Node 导入均在测试文件中。
- 主窗口启用 `sandbox: true`、`contextIsolation: true`、`nodeIntegration: false`。
- 自定义图片协议、外部导航、路径信任、窗口级工作区范围和 IPC 输入均有主进程校验。
- 保存链路具有 `expectedMtime`、内容哈希、显式强制覆盖、串行锁和恢复日志。
- Milkdown/ProseMirror 仍是正文状态源，没有发现另建一套可独立编辑正文状态的架构倒退。

当前没有重写 Electron、React 或 Milkdown 技术栈的证据。战略投入应放在端到端正确性、产品闭环和发行，而不是框架迁移。

### 4.2 当前阻断项

| 级别 | 发现 | 证据与影响 | 处理原则 |
| --- | --- | --- | --- |
| P0 发行 | Electron 核心冒烟失败 | `npm run smoke` 两次稳定返回：新建文档 `INVALID_TARGET`。构建成功不能替代此链路 | 发布候选前修复并增加 Windows 路径别名端到端回归 |
| P0 门禁 | 冒烟涉及 Windows 短路径与真实路径不一致 | `os.tmpdir()` 为 `C:\Users\ADMINI~1\...`，`realpath` 为 `C:\Users\Administrator\...`；窗口工作区校验对不存在目标回退字面路径，最可能导致拒绝 | 统一授权比较的规范化口径；修复前不要降低安全校验 |
| P0 性能 | 5000 篇合成库性能门禁失败 | 早前两次 Node 24 为树 315–347 ms、索引 3136–3571 ms、搜索 1844–1854 ms；本轮树 176.52 ms 已通过，但索引 3482.26 ms、搜索 1672.44 ms 仍超过 2000/1500 ms；Node 22 同样有失败 | 先分析环境、磁盘和脚本口径，再定位退化与波动；不得直接放宽阈值或覆盖基线 |
| P0 测试基础设施 | 生产搜索性能测试返回 `INVALID_TARGET` | `npm run perf:production` 为 2 个文件中 1 个通过、1 个失败；本轮冷索引 5624.66 ms 在 15000 ms 阈值内，搜索 IPC 没有进入性能测量 | 修正测试授权/路径口径，确保测试实际覆盖生产搜索 |
| P0 供应链 | 生产依赖存在 1 个高危漏洞 | `npm audit --omit=dev --audit-level=moderate` 报告 `js-yaml@4.3.1` CPU 消耗漏洞；由 `electron-updater` 等间接引入 | 评估安全升级并跑完整门禁；不直接执行无审查的 `npm audit fix` |
| P0 许可 | 根目录无 `LICENSE` | `package.json` 标记 MIT 不能单独构成清晰授权和分发材料 | GitHub 公测前确认代码、资源和第三方权利，补正式许可与声明 |
| P0 隐私与凭据 | 联网不可见、没有独立隐私说明 | 生产版启动会通过 `electron-updater` 检查 GitHub 更新源并自动下载；代码未设置 `autoInstallOnAppQuit`，库默认 `true`，已下载更新会在退出时安装，且没有关闭开关。用户启用 SM.MS 后图片会发送到第三方，其 token 当前明文存于 `userData/settings.json`。拼写检查默认关闭，打开后可能下载词典 | 外部 Alpha 前让检查、下载和退出安装都可关闭；使用系统安全存储迁移 token；隐私说明覆盖默认更新、主动上传和可选词典下载 |
| P0 分发 | 安装与更新未验证 | 未执行 `build:win` 安装循环；macOS 未签名/公证，Linux 桌面集成未验证 | 第一阶段明确 Windows-only 公测，完成安装、升级、卸载、文件关联与回退 |
| P0 维护 | 三个 `demo:soft*` 脚本引用不存在目录 | `design/soft-workbench` 当前不存在，贡献者会得到不可复现入口 | 删除失效脚本或恢复真实资产，文档与脚本保持一致 |
| P2 体积 | Renderer 存在多个大包 | Milkdown 约 1.85 MB，主入口约 1.53 MB，另有 Mermaid/图谱大 chunk | 先测安装体积、冷启动和首个编辑时延，再按真实瓶颈懒加载；不按包大小盲目重写 |

上述 Windows 短路径差异是基于当前环境和代码路径得到的高可信原因候选，尚未通过新失败测试完成最终证明。它可能首先表现为冒烟夹具问题，但同类短路径、别名路径或恢复路径也可能进入真实产品，因此必须按产品授权一致性问题处理。

### 4.3 文档与现实的偏差

旧状态记录正确保存了 2026-09-20 当时 `smoke` 通过的历史证据，但当前 `HEAD` 上新鲜执行已失败。战略和发行判断必须采用本轮结果，不能沿用历史绿灯。

同样，上一轮工程任务完成不等于产品阶段完成。两位现有用户研究表仍未采集，外部使用、重复价值、付款和团队研究均未执行；因此不能从“1549 项测试”推导出用户会采用、会付费或团队可以部署。

## 6. 竞争格局

Paperin 实际面对四类竞争者：单篇 Markdown 编辑器、个人知识系统、云端工作知识库、开发者现有工具链。用户也可能选择资源管理器搜索和手工复制粘贴，这种“不换工具”同样是竞争。

### 6.1 主流产品对照

| 产品 | 核心优势 | Paperin 不应正面复制 | Paperin 可形成的差异 |
| --- | --- | --- | --- |
| Obsidian | 本地 Markdown、链接/属性、Bases、插件生态、Sync/Publish | 插件数量、社区生态、全面个人知识系统 | 更少配置地完成“查资料、插来源、写技术文档、交付”完整任务 |

| Joplin | 多端笔记、同步、可选端到端加密、长期用户基础 | 跨设备笔记和同步基础设施 | 直接维护用户项目中的 Markdown，而不是应用内部笔记库 |
| Zettlr | 学术写作、引用管理、项目和多格式输出 | 学术文献工作流和成熟引用生态 | 技术/项目文档来源复用与软件项目资料维护 |
| VS Code + Git | 代码与文档同仓、扩展、预览、链接检查、版本审阅 | 开发者生态、Git 能力和可编程性 | 给不想装配插件的人提供更专注、更可发现的文档工作台 |
| 飞书知识库 | 组织空间、多类型文档、权限、协作和企业集成 | 组织治理和实时协作 | 个人原稿、离线资料和向团队交付前的准备阶段 |
| Confluence | 团队空间、评论、权限、版本、Jira 集成 | 企业协作、审计和平台集成 | 小团队文档作者端、标准文件与轻量交付 |
| Outline / GitBook | 团队知识库或面向读者的文档发布体验 | 托管、权限、发布站点和运营 | 本地创作与维护源文件，再输出到现有发布/团队渠道 |

### 6.2 Paperin 的战略空位

Paperin 不应宣传成“Typora + Obsidian + 语雀”。这句话等于同时承担三类成熟产品的维护义务，也无法告诉用户为什么今天要换工具。

更可行的空位是：

> **比 Typora/MarkText 更懂跨文档资料复用和持续维护；比 Obsidian/VS Code 更少配置、更聚焦成稿；比语雀/Notion/飞书更本地、更尊重原始文件；比块式知识工具更围绕完整技术与项目文档。**

这个空位不是完全无人占据，但与当前代码资产高度匹配。真正需要证明的不是功能是否存在，而是用户能否在没有教学的情况下更快完成真实任务，并愿意下一次继续使用。

### 6.3 不能宣称的优势

目前不能宣称：

- 最快、最轻或性能领先。
- 比 Obsidian 更强的知识管理。
- 比 Typora 更成熟的写作体验。
- 无损支持所有 Markdown 方言和所有导出格式。
- 全平台稳定、企业级安全或团队协作完备。
- AI 原生、智能知识库或可替代专业文献管理器。

## 7. 应强化的产品优势

### 7.1 文件主权与低迁移成本

用户直接拥有普通 Markdown 和附件，不要求账号，不把迁出自己的文件设为付费能力。这能降低尝试成本，也能与 Obsidian、Typora、VS Code、Git 和同步盘共存。

它不是独占功能，因此需要与下面三个优势组合表达。

### 7.2 来源就在写作流程里

当前代码已有工作区搜索、反链、片段预览、插入引用、相对链接和位置恢复。最有辨识度的演示不是图谱或九套主题，而是：

1. 从旧方案、排障记录或接口文档中找到依据。
2. 把带来源的片段插入当前技术说明。
3. 继续写作并可撤销。
4. 保存、重开和导出后来源仍可理解。

这是当前最接近产品差异化的完整能力组合。

### 7.3 文档生命周期可信

冲突检测、版本绑定保存、恢复写入、草稿、关闭保护、索引完整性说明和导出预检，能够形成“值得托付项目文档”的长期优势。它的护城河不是一句“本地优先”，而是持续积累的故障夹具、恢复协议和透明边界。

在当前 smoke 和性能门禁恢复前，这项优势应表述为“已建立深入保护，正在完成发行验证”，不能提前宣传为绝对可靠。

### 7.4 从原稿到交付

Paperin 已具备多格式和集合输出基础。未来可将专业交付做成个人 Pro 价值：可重复的导出配置、项目文档包、来源/断链/缺图报告、统一样式和接收方兼容检查。

这比新增另一个知识面板更接近可付费结果，因为用户为减少返工和稳定交付付费，而不是为菜单数量付费。

## 8. 产品边界与优先级

### 8.1 现在做

- 修复 `INVALID_TARGET` 的真实 Electron 新建链路和性能测试授权链路。
- 解释并处理 5000 篇性能门禁退化，不修改阈值掩盖问题。
- 升级或约束存在高危漏洞的间接依赖，并跑全量回归。
- 删除指向不存在目录的 `demo:soft*` 脚本。
- 让更新检查、自动下载和退出时安装可见、可关闭；SM.MS token 迁入系统安全存储。
- 补根许可证、第三方许可、资源权利说明，以及覆盖三类联网路径的隐私说明。
- 完成 Windows 安装、文件关联、升级、卸载和数据保留验证。
- 两位现有用户的两周任务记录可与上述工程修复并行采集，但是 P1 进入条件，不作为 P0 退出条件。
- 将首次 15 分钟核心任务打磨成无口头提示可完成的流程；该项同样属于 P1，不阻塞 P0。

### 8.2 下一步做

- 招募 6–8 位符合画像的外部用户做对照任务。
- 优化来源预览、插入、失效检查和再次维护体验。
- 收敛 HTML/PDF/DOCX 的明确支持矩阵和接收方验证。
- 建立 GitHub 候选发布、问题模板、诊断包和隐私说明。
- 在外部 Alpha 发布时编写真实的 `CHANGELOG.md` 与 `CONTRIBUTING.md`；它们不是 P0，也不提前放空文件。
- 基于实际瓶颈优化冷启动、索引、搜索和大文档体验。

### 8.3 有证据后再做

- 专业导出配置、项目交付包和文档健康报告。
- 与 Git 工作流更自然的状态展示和交接，但不重造 Git。
- 小团队的文档责任人、评审状态、变更摘要和交付清单。
- 可选 AI：只在选定资料范围内查依据、生成带出处草稿或检查变更。
- 可选同步：先支持并解释现有 Git/同步盘冲突，再决定自建服务。

### 8.4 当前不做

- 实时多人协作和评论后台。
- 企业账号、SSO、RBAC、审计和组织控制台。
- 通用 PDF/Office/OCR 全文资料库。
- 插件市场和第三方 API 稳定承诺。
- 移动端和 Web 全功能版。
- 全库自动 AI 问答、智能体执行文件操作或默认上传正文。
- 为追赶竞品而建设数据库、白板、日记、任务管理和项目管理全家桶。

## 9. 分阶段路线图

路线图使用退出条件而不是只使用日期。以每周约 20 小时有效投入估算，时间可顺延，门槛不可跳过。

### 阶段 0：恢复可信候选基线（0–4 周）

目标：形成可在 Windows 上重复安装、联网行为已披露、可交给现有两位用户试用的候选包。两位用户的任务记录不阻塞本阶段退出。

交付：

- Electron smoke 全绿，覆盖打开工作区、新建、保存、冲突、重命名、搜索、关闭与系统文件关联。
- Node 22 下 lint、typecheck、1549+ 测试、build、a11y、性能门禁全部绿。
- 解释性能退化根因；若是环境基线变化，保留多轮和设备证据后再调整阈值。
- 自动更新的检查、自动下载和退出时安装都可见、可关闭；关闭后不得在下次退出时安装已下载的包。SM.MS token 完成系统安全存储迁移，失败时可靠降级为本地附件。
- 处理高危依赖，删除失效 `demo:soft*` 脚本，补许可证、第三方声明、隐私说明和安全响应入口。隐私说明必须覆盖默认更新全流程、用户主动的 SM.MS 上传，以及打开拼写检查后可能的词典下载。
- Windows 安装包在至少两个隔离环境完成安装、升级、卸载、文件关联和用户文件保留验证。
- 两位用户研究可以与工程修复并行启动，但不阻塞 P0 工程基线收敛；其结果必须在外部 Alpha 发布前完成。

退出条件：没有 P0 数据/发行阻断；候选包可重复安装；所有默认和可选联网行为已准确披露。两位用户记录是外部 Alpha 发布门槛，由阶段 1 的首项任务验收。

### 阶段 1：GitHub 外部 Alpha（1–3 个月）

目标：证明陌生用户能理解定位并独立完成核心任务。

首批画像：已有 Markdown 项目资料，需要持续编写技术说明、方案、README、决策记录、排障文档或项目手册的个人贡献者。优先独立开发者、技术作者、实施/运维和维护项目文档的产品/研发人员。

交付：

- 一个真实、脱敏的示例项目，展示“旧资料 -> 来源引用 -> 技术说明 -> 导出”。
- GitHub Release 候选与稳定通道、安装说明、已知限制、隐私说明、安全响应渠道、反馈模板、`CHANGELOG.md` 和 `CONTRIBUTING.md`。后两份只在真实发布时按当次版本和贡献方式编写，不作为 P0 空文件。
- 6–8 位外部发现样本，至少一半不是熟人。
- 在常用工具与 Paperin 之间做等价任务对照，不剥夺竞品插件和正常配置。
- 根据最大阻塞只做一个主要产品增量，不同时启动 AI、同步和团队功能。

退出条件：大多数目标用户无需口头教学完成核心任务；保存/重开/导出没有内容损坏；至少 3 位用户在第二个真实任务中主动再次使用。

### 阶段 2：个人专业版与公开 Beta（3–6 个月）

目标：从“能用”进入“愿意持续使用并为明确结果付费”。

重点能力：

- 来源健康：来源文件移动、断链、失效或内容变化时给出可解释提示。
- 维护工作流：项目文档模板、变更摘要、更新时间、待确认来源和交付检查。
- 专业交付：保存导出配置、项目文档包、统一样式、接收方兼容报告。
- 性能与稳定性：真实 1k/5k 文档库、复杂 5 MiB 文档、8 小时运行和第二台设备。
- 低支持成本：诊断信息不含正文/绝对路径，用户可自助理解问题。

退出条件：形成至少 20 位激活用户的四周观察队列；W4 有效留存目标 40%；至少 25% 的活跃用户发生资料复用；至少 5 位非关联用户完成真实付款实验。所有比例必须同时报告样本量和失访。

### 阶段 3：团队交付桥梁（6–12 个月，有条件）

进入条件：至少 3 个小团队重复提出同一类交付、评审或共同维护问题，且个人版已有稳定外部使用。

推荐先做：

- 与 Git、共享目录、语雀、飞书、Confluence 等现有渠道共存的交付包。
- 文档责任人、评审状态、更新时间和变更摘要等可移植元数据。
- 团队文档健康报告、断链/缺图/来源状态和交付清单。
- 明确的并发修改与冲突策略，不把共享目录包装成实时协作。

不先做账号中心、实时协同编辑和复杂权限。团队价值应从“个人作者把可靠成果交给团队”自然延伸。

退出条件：3 个团队连续两个周期使用同一工作流，能够说明节省的返工、交接或维护成本，并出现真实预算或采购意向。

### 阶段 4：企业内部知识库（12 个月以后，有预算和团队后）

企业版不是个人版多加一个登录按钮。它至少需要：

- 身份、组织、SSO、RBAC、空间与文档权限。
- 审计、保留策略、备份恢复、密钥和数据边界。
- 并发、评论、评审、通知、管理员控制和生命周期治理。
- 私有部署、升级、兼容、监控、SLA、安全响应和支持责任。

只有在团队试点证明需求、有稳定收入且至少有专门维护能力后，才应单独立项。届时很可能需要新增服务端和同步架构，不能继续把本地单机应用直接称为企业知识库。

## 10. 用户验证与指标

### 10.1 北极星指标

推荐北极星：

> **每周使用既有资料完成并实际交付或继续维护一份文档成果的活跃用户数。**

“创建笔记数”“启动次数”“停留时长”和“图谱节点数”只能作为诊断指标，不能代表价值。

### 10.2 核心漏斗

| 阶段 | 事件 | 建议指标 |
| --- | --- | --- |
| 安装 | 成功安装并打开自己的目录 | 安装成功率、首次错误、支持时间 |
| 激活 | 找到来源、插入引用、保存重开、导出 | 15 分钟内独立完成率；失败步骤 |
| 重复价值 | 在下一次真实任务继续使用 | 按人记录的 W1/W4 有效留存 |
| 资料复用 | 旧资料进入新文档并保留来源 | 每周发生有效来源复用的用户占比 |
| 交付 | 接收方能正常阅读成果 | 缺图、断链、格式返工和失败率 |
| 商业 | 为明确结果付款并继续使用 | 付款人数、退款、30 天使用、支持成本 |

### 10.3 两位现有用户的最小研究

连续两周，每人至少记录 3 次真实任务：

- 任务和最终成果是什么。
- 原本会使用什么工具。
- 从哪里找到资料，是否插入来源。
- 哪一步需要解释、绕路或失败。
- 保存重开和交付是否正确。
- 下一次是否主动继续使用。

不要计算“两人中一人回来等于 50% 留存”。两人阶段只做逐人因果分析。

## 11. 商业化建议

### 11.1 原则

- 不对读取、保存、恢复或取回用户自己的 Markdown 收费。
- 不在产品价值未验证前开发复杂授权、账号和支付后台。
- 收费对象是专业结果、持续服务或团队治理，不是基础数据自由。
- 开源与商业策略必须先解决根许可证和第三方权利问题。

### 11.2 推荐顺序

| 阶段 | 方案 | 目的 |
| --- | --- | --- |
| 种子期 | 赞助/支持维护，所有核心能力保持一致 | 验证是否有人愿意支持，不据此预测收入 |
| 外部 Alpha 后 | 99–199 元人民币的创始用户支持包或预购实验，不先做自动授权 | 验证真实付款，不用“愿意付费”问卷代替 |
| 个人成熟期 | 免费核心 + 个人 Pro | Pro 可包含专业导出配置、项目交付包、文档健康报告和高级维护流程 |
| 商业模型验证 | 对比一次性许可与年度维护 | 一次性更符合桌面工具直觉；年度维护更匹配持续兼容成本，依据真实转化选择 |
| 团队阶段 | 按团队/席位的管理和支持方案 | 前提是团队治理功能和支持能力真实存在 |

价格仅是实验区间，不是当前承诺。首次实验至少需要 5 位非关联用户真实付款，并记录退款、30 天使用和每位用户支持时间。若连续两轮没有付款理由，暂停收费功能，回到任务价值而不是继续包装套餐。

### 11.3 最可能的个人 Pro 价值

- 可保存和复用的多格式导出配置。
- 技术手册/项目文档集合交付包。
- 来源、断链、缺图、过期和不支持格式报告。
- 专业项目模板与维护清单。
- 批量检查和交付前兼容验证。

AI 和同步具有持续成本，在单位成本、隐私边界和重复需求未验证前不适合作为首个收费支柱。

## 12. GitHub 发布与增长策略

GitHub 的首要作用是获得高质量试用与可信反馈，不是追求 Star 数。

推荐发布物：

- Windows 候选安装包和校验信息。
- 一段 2–3 分钟的完整任务演示，不做功能巡礼。
- 一个脱敏的技术项目示例库。
- 清楚列出支持范围、已知限制、数据存储位置和卸载后的文件归属。
- `bug`、兼容性、数据安全、功能建议四类 Issue 模板。
- 每个版本公开 smoke、测试、安装和已知未验证项。
- 与该次发布对应的 `CHANGELOG.md` 和说明如何报告问题、如何贡献的 `CONTRIBUTING.md`。二者随 P1 Alpha 发布编写，不进入 P0，也不用占位正文提前入库。

推荐内容主题：

1. 用旧排障记录写一份带来源的技术说明。
2. 用本地 Markdown 维护项目决策、README 和接口资料。
3. Paperin 与 Obsidian、Typora、VS Code、语雀如何共存，而不是强迫迁移。

增长判断以“合格安装 -> 独立完成 -> 第二次任务 -> 实际成果”漏斗为准。下载和 Star 没有进入真实任务时，不继续扩大推广。

## 13. AI 主导开发的治理方式

AI 是产能来源，不是需求来源、用户代表或发布责任人。建议固定以下流水线：

```text
真实问题/门禁失败
  -> 明确用户行为与风险
  -> 先写失败测试
  -> 最小实现
  -> 代码与安全边界复核
  -> 全量门禁
  -> 真实 Electron/安装态验证
  -> 文档与变更记录
  -> 候选发布
```

治理规则：

- 同一时间只推进一个主产品目标，避免多个 AI 会话扩大未验证代码面。
- 任何“完成”都绑定当前提交和新鲜命令输出，历史通过不自动继承。
- 对文件、IPC、编辑器和导出变更，单元测试通过后仍必须跑真实 Electron 链路。
- 超过 450 行的文件不继续添加功能；超过 300 行先评估职责。
- 每两周至少留一个时段只做用户任务、清理失效入口和验证安装包。
- 不让 AI 自动调整性能阈值、静默忽略失败或生成虚构用户研究结果。

## 14. 主要风险与应对

| 风险 | 早期信号 | 应对 |
| --- | --- | --- |
| 定位重新变宽 | 路线图同时出现 AI、同步、数据库、团队、移动端 | 每季度只保留一个核心用户结果，其他进入条件项 |
| 自动测试制造成熟错觉 | 测试全绿但 smoke、安装或真实任务失败 | 将 Electron、安装态和用户任务列为独立门禁 |
| AI 生成带来维护膨胀 | 大文件增长、重复状态、相似实现分叉 | 触及即拆、契约测试、每轮 diff 审查 |
| 数据信任受损 | 一次静默覆盖、乱码保存或错误成功提示 | P0 处理、发布说明、故障矩阵和可恢复设计 |
| 发行支持失控 | 多平台同时承诺、安装问题大量出现 | 先明确 Windows 公测，按平台逐个开放 |
| 与 Obsidian/Typora 同质化 | 宣传只剩“本地、Markdown、主题、图谱” | 始终用来源复用和项目文档交付任务表达价值 |
| 商业化过早 | 先做授权系统，没有重复用户 | 先做人工小额真实付款实验 |
| 团队扩张过早 | 开始做账号权限，却没有团队任务样本 | 以 3 个团队重复需求作为进入门槛 |
| 许可不清 | GitHub 发布时只有 package 的 MIT 字段 | 发布前补根许可、资源来源和第三方声明 |

## 15. 决策清单

### 立即确定

- 产品类别：本地 Markdown 项目知识工作台。
- 首批用户：维护技术与项目文档的个人贡献者。
- 核心任务：从自己的资料中找到依据，写成可维护、可交付的文档。
- 首发平台：建议先 Windows；其他平台只有通过各自安装门禁后再承诺。
- 当前产品阶段：私有种子/候选，不称正式成熟版。
- 当前商业策略：免费验证，不开发收费系统。

### 用证据决定

- 个人 Pro 选择一次性许可还是年度维护。
- 优先强化项目文档维护还是专业导出。
- 是否需要可选 AI、同步或 Git 增强。
- 是否进入团队产品，以及团队能力的第一项具体任务。

### 明确否决

- 通过增加功能数量与成熟竞品对齐。
- 在 smoke、性能、安全依赖和安装证据未通过时公开正式发布。
- 以两位用户、下载量或测试数量宣称产品市场匹配。
- 直接把共享目录称为团队协作或企业知识库。

## 17. 最终判断

Paperin 当前最有价值的不是“已经拥有多少 Markdown 功能”，而是已经形成三个可组合的基础：标准本地文件、来源进入写作的闭环、较深入的数据可靠性工程。它们足以支撑一个有辨识度的个人产品，但尚未自动构成市场优势。

正确的发展方向是先成为技术与项目文档作者可信赖的本地工作台，再把专业交付做成个人商业价值，然后从“作者向团队交付”进入小团队，最后才考虑企业治理。这个顺序既符合现有代码，也符合晚上和周末投入、AI 为主要工程产能、两位种子用户的现实。

近期成功标准只有一个：**陌生目标用户不需要开发者在旁指导，就能用自己的资料完成一份带来源的真实文档，安全保存并交付，而且下一次还愿意继续用。**
