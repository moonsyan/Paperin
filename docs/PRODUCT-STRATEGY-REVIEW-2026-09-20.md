## 1. 核心判断与决策建议

**Paperin 已经越过界面原型阶段，拥有较完整的本地 Markdown 知识工作流；目前处于两位种子用户使用、工程可靠性继续收敛、产品价值尚待外部验证的阶段。** 当前不适合用“功能完成百分比”评价，更不能由测试数量推导出产品成熟度。

建议强化的定位是：

> **Paperin 是面向技术与项目工作的本地 Markdown 知识工作台，帮助用户整理自己的资料、带着来源写作，并持续维护和交付项目文档。**

面向新用户的短表达：**把自己的资料，写成持续有用的文档。** 配套说明应立即告诉用户：直接打开 Markdown 文件夹，查找并引用旧内容，完成技术文章、方案与项目文档。

这一定位能够串起用户提出的知识库管理、资料管理、写作、技术文档和项目文档维护，且与现有工作区、检索、来源引用、模板、诊断和导出实现相符。近期“资料”明确指 Markdown、图片及关联链接；用户已确认先打磨 Markdown，不在本阶段承诺 PDF/Office 全文资料管理。

本轮建议作出六项取舍：

1. **以技术与项目文档的完整任务为主线。** 将“找到旧资料 → 引用到当前文档 → 安全保存 → 正确交付 → 下次继续维护”作为产品验收单位。
2. **先修已确认的信任缺口。** 异常编码、旧保存基线、搜索覆盖、集合导出保真优先于新增功能。
3. **把已经存在的能力连顺，而不是重新建设。** 搜索引用、恢复位置、模板、导出预检已有实际实现，下一步是纠错、发现入口和真实任务验证。
4. **先做个人产品，再验证个人付费，团队按条件进入。** 三者是递进的业务阶段，不是现在并列开发的三个产品。
5. **保留标准文件与外部工具共存。** 争取成为一个有价值的日常入口，允许用户继续用 Obsidian、Typora、VS Code 和团队平台。
6. **按每周可持续投入约 20 小时排工作。** 周末可集中开发不等于有全职团队；每周最多一个主要产品增量，并保留故障与研究时间。

## 3. 实际产品状态：已形成工作台，尚未形成成熟交付产品

### 3.1 代码资产与工程状态

基线包含 536 个受版本管理的 `src` 文件，其中 501 个 TypeScript 文件；排除 `.test` 和 `.perf` 后为 311 个生产 TypeScript 文件、43,283 个物理行。`src` 下有 188 个 `.test.ts/tsx` 文件，另有脚本测试，文件数不等于执行通过数。

架构已经分为 Main、Preload、Shared、Renderer。Main 承担文件和索引，Preload 提供窄类型桥接，编辑器基于 Milkdown/ProseMirror。代码中有保存队列、会话身份、内容哈希、恢复日志、路径信任、正则 Worker、索引缓存及多种失败分支。这些是可继续投入的基础，**目前没有证据支持为了产品定位重写技术栈**。

本轮类型检查与生产构建通过；`lint` 失败，包含 1 个未使用导入错误和 3 个 Hook 依赖警告。主题与焦点静态门禁通过，但主题检查有 37 项存量基线豁免。全量测试为 190 个文件通过、3 个因 Electron 运行时缺失加载失败，执行到的 1,374 项通过；桌面冒烟也被运行时缺失阻塞。二进制恢复下载超时，本轮没有获得桌面运行验证。详情见附录。通过的自动测试不能覆盖下述所有定向复现问题。

### 3.3 容量承诺必须分层

| 层次 | 当前实现约束 | 不能推导出的承诺 |
| --- | --- | --- |
| 打开/保存 | 单篇 20 MiB 守卫 | 20 MiB 任意结构编辑流畅、具备同等级历史恢复 |
| 文件树 | 2,000 节点、深度参数上限 5 | 所有合法打开的库都能完整展示 |
| 全文搜索 | 5,000 文档、单篇不超过 2 MiB、最多 200 条命中，沿用树深度限制 | 全文“没有结果”一定等于资料不存在 |
| 统一索引 | 5,000 文档、单篇不超过 2 MiB；枚举深度与树/搜索不同 | 图谱、标签、搜索和侧栏始终覆盖同一集合 |
| 版本历史 | 单篇源文件不超过 2 MiB；每篇最多 20 份且总计 5 MiB | 可打开的每篇大文档都有历史版本可恢复 |
| 5 MiB 性能场景 | 固定约 256 个长段落的合成文档，有历史开发机通过记录 | 大量短段落、表格、公式、图表也一定达标 |

这些预算本身可以是合理的资源保护。产品问题是**边界不统一、跳过原因不总能被用户看到**。应先统一范围解释和诊断，再根据真实资料规模优化，而不是直接把所有上限调大。

| 维度 | 本轮判断 | 依据 |

## 4. 本轮发现如何影响产品优先级

附录给出文件位置、复现输入、证据层次和处理建议。本节聚焦产品影响。

| 级别/编号 | 发现 | 对目标用户的影响 | 建议 |
| --- | --- | --- | --- |
| P1 / A01 | 残缺带 BOM UTF-8 返回替换字符；奇数字节 UTF-16LE 丢尾字节 | 用户可能把被宽松解码的内容再次保存 | 最先补测试和严格解码/明确恢复选择；不能静默“修好” |
| P1 待端到端定级 / A02 | 旧 `expectedMtime` 落在 500ms 容差内，最新全局哈希可让纯函数放行 | 多窗口/短间隔写入的旧基线保护可能失效 | 将保存绑定到读取版本；先复现完整双窗口再定修复边界 |
| P1 / A03 | 集合导出 frontmatter、脚注、引用式图片和嵌套列表失真 | 项目手册或文章合集可能缺内容、丢来源或暴露元数据 | 暂不宣传集合交付稳定；统一渲染契约与完整性夹具 |
| P1 交付 / A04 | 内联图片失败仍可能提示成功；输出范围存在静默回退 | 发给别人后才发现缺图或只输出一篇 | 将完成反馈与实际产物、范围和失败数一致绑定 |
| P2 / A05 | 搜索大文件/深层目录被跳过但可报告完整 | 用户错误判断资料不存在 | 显示覆盖率口径与跳过原因；统一树、索引、搜索策略 |
| P2 / A06 | watcher 对目录/未知路径事件过滤；单个坏编码可能使全次扫描失败 | 外部维护项目文档后列表或关联信息可能失效 | 补目录级失效和逐文档错误隔离 |
| P2 / A07 | fresh 窗口不持久化同等草稿；搜索/发布弹窗焦点支持不齐 | 恢复预期和键盘使用不一致 | 明确边界并固化真实窗口、输入法和焦点测试 |
| 门禁 / A08 | lint 非零；发布流程直接非草稿发行，安装证据不足 | 开发成功不能直接转成可靠发行 | 修基线，建立候选验证再发布的可执行流程 |
| 维护 / A09 | 多个超限文件、集合与编辑器两套渲染语义、文档状态滞后 | 单人维护成本和后续回归风险上升 | 随修复拆职责，不开展整仓重写 |

这里没有宣称已发生用户数据损失，也没有把纯函数问题等同完整攻击链。高风险发现应进入“信任问题先处理”的通道，而不是与新增主题、图谱或增长功能做普通收益排序。

### 5.1 竞品对照

| **Joplin** | 笔记、待办、同步和可选端到端加密 | 跨设备笔记与既有资料收集流程 | 直接维护自己的 Markdown 项目目录；Joplin 同步文件不应当作可随意编辑的普通 Markdown 源目录。跨设备是 Paperin 当前缺口。[产品说明](https://joplinapp.org/help/)、[FAQ](https://joplinapp.org/help/faq/)、[加密](https://joplinapp.org/help/apps/sync/e2ee/) |
| **飞书文档/知识库** | 组织知识空间、多类云文档、层级组织与权限治理 | 团队已经在同一组织环境内协作 | 在个人素材、方案准备和交付阶段配合使用；本地保存不等于具备组织权限管理。[知识库介绍](https://www.feishu.cn/content/knowledge-management-strategies)、[权限说明](https://www.feishu.cn/hc/zh-CN/articles/265017155035) |
| **Confluence** | 空间/页面、实时编辑、评论、版本、权限及 Jira 等工作联系 | 团队治理和项目协作上下文 | 小型项目的个人作者端与静态交付可能互补；多人治理不是多加一个分享按钮。[官方功能](https://www.atlassian.com/software/confluence/features) |
| **VS Code + Git** | Markdown 预览、路径/标题补全、链接检查、引用查找、重命名更新链接等 | 技术用户已有工具链，代码与文档同仓维护 | 最直接的项目文档替代方案之一；必须证明编写/复用/交付更顺，而不能只比较笔记产品。[Markdown 文档](https://code.visualstudio.com/docs/languages/markdown) |

真正的替代品还包括资源管理器搜索、手动复制粘贴和继续使用现有工具。用户有痛点，并不自动意味着愿意多安装一个工作台。

### 5.2 对竞争方向的选择

| 路线 | 匹配度与成本 | 判断 |
| --- | --- | --- |
| 做更完整的通用 Markdown 编辑器 | 用户容易理解，但直接进入 Typora/MarkText/VS Code 的成熟领域，差异容易落到皮肤与价格 | 保留优秀编辑体验作为基础，不作为全部战略 |
| 做技术与项目工作的本地知识工作台 | 可以复用现有搜索、来源引用、模板、诊断和输出，用户任务可观察 | **近期主线** |
| 做全面个人知识系统 | 会进入块、数据库、移动、插件等竞争，需要持续扩大维护面 | 按任务需求谨慎吸收，不追求功能表对齐 |
| 做团队/企业知识库 | 权限、并发、审计、运营与支持要求不同，当前代码和人力不足 | 保留后续探索，先从作者到团队的交付边界进入 |

“Typora 的写作 + Obsidian 的知识管理 + 语雀的协作”可以帮助解释灵感，但不适合当路线图：它把三套成熟系统的维护义务同时交给一位兼职开发者。

## 6. 优势体系：哪些已经具备，哪些需要证明

### 6.1 已有且可展示的资产

**第一，源文件直接属于用户。** 普通 Markdown 和附件可被其他工具使用，退出产品无需先导出整套专有数据库。这降低试用阻力，是重要承诺；但 Obsidian、Typora、MarkText 等也有重叠，不能称独占。

**第二，知识管理靠近正在写的文档。** 搜索/反链插入来源快照、保留相对链接并返回原位置，是已落地的组合能力。演示应该展示这段路径，而不是逐个展示图谱、标签和面板。

**第三，技术内容与项目文档已有基础。** 代码、公式、图表、六类模板及导出预检支持技术作者工作；相比泛化个人日记定位，更容易提出具体价值和测试任务。

**第四，数据可靠性投入较深。** 路径授权、哈希冲突、保存会话和恢复日志是有用的工程资产。正确的表达是“已建立保护并持续公开验证边界”，不是“永不丢数据”或“比所有竞品更安全”。

### 6.2 需要通过用户任务证明的优势

| 候选优势 | 当前依据 | 如何证明成立 |
| --- | --- | --- |
| 少配置就能完成资料复用 | 内置流程存在 | 用户无需教程或插件配置，独立找到来源、插入并继续写作 |
| 项目文档维护更连续 | 工作区、模板、链接与诊断 | 一周后更新旧文档、核对来源并再次交付，仍选择 Paperin |
| 更值得托付本地资料 | 保存/恢复设计和测试 | 已知高风险问题关闭，适用故障矩阵通过，用户理解恢复和迁出方式 |
| 输出可以直接用于工作 | 有多条导出链路 | 在接收方软件打开后正文、图、来源、层次完整，而不只是文件生成成功 |
| 中文写作更省心 | 中文场景与主题设计 | 真实中文 IME、常见缩放、长时间使用和配对任务结果支持 |

尚不能证明的词包括“最快、最轻、最可靠、无损兼容所有 Markdown、全面替代 Obsidian、企业级”。主题数量、代码行数、测试用例数、功能菜单长度也不是护城河。

### 6.3 可逐步积累的竞争力

真正值得积累的是技术文档兼容夹具、故障与恢复回归库、可复用的项目工作流、低支持成本的上手体验，以及真实使用者愿意展示的成果案例。这些资产可被复制，但持续积累能提高产品一致性和用户信任。两位用户阶段还不适合宣称网络效应或数据壁垒。

## 7. 目标用户与产品边界

### 7.1 首批重点服务谁

第一优先是**已有 Markdown 资料、需要持续写或维护技术/项目文档的个人贡献者**：开发者、技术负责人、实施/运维人员、技术作者，以及用 Markdown 写方案的产品人员。筛选依据是任务，不是职业头衔。

典型任务：“我已经有旧方案、接口说明和排障记录，需要从中找出依据，更新一份设计说明，并交给同事阅读；以后还要继续维护。”

第二优先是有稳定产出的技术内容作者。两者共享检索、来源、连续写作和交付能力，可以使用相同产品底座。泛兴趣收藏、移动随手记、学术文献管理、数据库看板和实时多人协作为相邻需求，先记录，不同时扩建。

招募先了解真实文件数量、最大文件、目录深度、常用输出、外部 Git/同步方式；不把“有 5,000 篇资料”设成必须满足的门槛，也不假设两位现有用户就是典型市场。

### 7.2 三个核心任务

| 任务 | 用户成功的定义 | 不应混入的扩张 |
| --- | --- | --- |
| 整理与找回 | 打开自己的目录，理解覆盖范围，定位需要的内容与来源 | 全文件格式 OCR、通用网盘、无限容量 |
| 理解与编写 | 引用旧资料，写出当前结论，保存后再次打开仍完整 | 仅堆收藏数量、为了图谱而强迫建链接 |
| 维护与交付 | 更新旧文档、发现失效引用、交付正确产物并保留原稿 | 立即做企业审批、多人实时编辑与全平台发布服务 |

“项目文档维护”先指个人作者维护项目文件与成果。任务列表、文件历史和多个窗口不等于项目管理系统、Git 版本控制或团队协作。

## 8. 产品与技术发展方向

### 8.1 按用户路径收敛能力

1. **进入工作区：** 保留直接打开文件夹；示例内容让用户完成一个小任务；初次任务优先打开/继续文档。手动开库自动显示图谱是否有效，用观察决定，不先做整套视觉重设计。
2. **查找资料：** 统一“搜了什么、没搜什么、为何跳过”；保留搜索输入与定位；把来源预览和引用插入做成容易发现的动作。
3. **写作与维护：** 优先保证中文输入法、末次输入保存、文件切换、标题/路径一致。模板围绕实际任务使用，不再按数量扩增。
4. **确认内容健康：** 先做确定性的缺图、断链、来源失效、输出不支持项；不要为“质量检查”自动改写正文。
5. **交付成果：** 先保证单篇 Markdown/HTML/PDF；DOCX 明确支持子集；集合输出先修保真再扩大使用。已有其他入口保持真实依赖和限制说明，不再增加格式竞赛。

### 8.2 保留的架构原则

标准 Markdown 是正文源，缓存和索引可重建，历史与草稿需独立保护。继续沿用 Electron/React/Milkdown 与窄 IPC，保持 Main 文件权限边界；异步保存绑定文档和编辑版本。避免为产品定位再创建第二套正文状态。

优先统一多条输出路径的语法契约。可以共享 AST 解析/转换边界与兼容测试，但本报告不预先规定必须把所有输出强行改成同一库；应先验证脚注、引用图片、frontmatter、列表、表格和公式的实际要求。

目录变化、索引范围、查询取消和读取失败应有清楚的服务契约。补逐文件诊断比遇到一篇坏文件让整个知识库不可用更符合产品目标。版本历史与独立备份的职责必须区分。

### 8.3 当前技术债处理方式

33 个生产 TypeScript 文件超过 300 行，8 个超过 450 行；其中 `demo-files.ts` 为示例数据，应与高耦合逻辑区分。`docx.ts`、工作区文件操作、设置、编辑器 overlays/instance、Mermaid、文件 IPC 是高维护关注点。详见附录。

每次修复只拆被触及的职责并补直接测试，不安排“先花两个月重构再做产品”。优先让导出、保存、索引这三个高价值边界可理解、可验证。构建产物体积也需实测，不仅凭 Electron 或 chunk 大小断言产品慢。

### 8.4 AI、同步和插件的进入条件

| 方向 | 合理的第一步 | 暂缓原因与进入条件 |
| --- | --- | --- |
| AI | 在选定资料中找依据、对引用给出处、辅助检查变更 | 搜索与来源正确性先成立；至少 5 位外部用户反复遇到确定需求；单独验证成本与发送范围。不是先做全库聊天 |
| 跨设备 | 先了解现有 Git/同步盘工作流和冲突 | 核心数据时序通过后，因缺移动/同步持续流失的证据出现；不能把支持普通目录称为全面同步安全 |
| PDF/Office 资料 | 若需求确认，先只读附件登记/打开，再单独评估全文提取 | 用户本轮已选择暂缓；文档格式、OCR、来源定位是独立产品面 |
| 插件平台 | 先稳定内部命令、面板与导出边界 | 至少多名外部开发者提出具体扩展并愿意维护；不为两位用户先建立长期兼容承诺 |
| 团队能力 | 个人原稿到团队阅读/评审的交付路径 | 先验证至少 3 个真实小团队的重复任务，再决定协作形态 |

## 9. 按个人时间预算安排的 12 周路线

### 9.1 容量假设

工作日约 `5 × 2 = 10` 小时；周末暂按两天合计 12–16 小时有效投入估算，总可用约 22–26 小时。**这是排期假设，不是开发者已承诺的精确工时。** 按每周 20 小时排计划，其余作为生活、复杂故障和上下文切换缓冲。

一个可持续的 20 小时分配是：实现与排障 12 小时、回归/人工验收 4 小时、用户观察 2 小时、文档与发布维护 2 小时。验收不可被新增功能挤掉。若实际只有 12 小时，缩减当周任务数，不削减数据安全验证。

### 9.2 分阶段建议

下面是决策性路线，不是未经测试估算的确定交付日期。工时包括相关测试与文档；出现复杂数据问题时顺延。跨平台资源和用户观察窗口不等同工程工时。

| 时段 | 主要结果 | 工作与估算 | 退出条件 |
| --- | --- | --- | --- |
| 第 1–2 周 | 建立可信修复基线 | A01 编码、A02 保存基线定向复现/修复、lint；约 30–45 小时 | 高风险输入与旧版本写入都有失败测试和正确处理；未结束则继续，不宣布可信发布 |
| 第 3–5 周 | 找到与交付的结果可信 | A03/A04 集合及图片保真、A05 覆盖口径、A06 目录变更；约 40–55 小时 | 核心语法夹具逐路径通过；输出范围、漏扫和失败均准确说明 |
| 第 6–9 周 | 两位用户到外部小样本 | 默认任务入口、适用平台候选验收、6–8 位外部试用；约 55–75 小时 | 实际平台通过门禁；外部用户能独立完成核心任务；修掉最大阻塞 |
| 第 10–12 周 | 看见重复价值 | 重复任务、次周回访、成果可读性、最大阻塞收敛；约 35–50 小时 | 有按人记录的持续任务与成果；能解释采用和放弃原因 |

合计约 160–225 小时，在 12 周约 240 小时的计划容量内留出缓冲。低样本招募从前期访谈开始，不等全部功能完工；已知数据风险关闭和适用平台安全验证前，只使用合成或可恢复的测试副本做操作研究。

本轮环境为 Windows，但用户没有指定正式支持平台顺序。建议先在实际用户使用的平台完成候选验证；若决定 Windows 先行，需同步支持声明与现有三平台发布计划。不能通过少测两个平台宣称三平台正式完成。

### 9.3 未来 3–6 个月

前 12 周完成且没有高风险回归后，选择一个延伸重点：**项目文档维护**或**专业交付**。前者围绕重命名后引用、文档更新和来源健康；后者围绕内容保真、模板化输出和可重复成果。选择依据为实际重复任务，最多一个主方向。

商业研究可以并行，但收费功能开发不应挤占可靠性。资源不足时继续做一个优秀个人工具同样是有效结果；团队版本不是必须按日期推出的里程碑。

## 10. 用小样本验证产品，而不是制造漂亮指标

### 10.1 两位现有用户阶段

连续两周，每人至少完成三次真实任务，记录：任务目的、原有工具、在哪一步停住、是否求助、最终成果是否使用、次日是否继续。记录脱敏结论即可，不建立遥测后台、不上传正文和路径。

两人中一人回来不是“50% 留存证明成功”。此阶段用逐人案例和重复行为找问题：哪些流程开发者自己都绕开，朋友在哪一步需要解释，哪些功能两人完全不用。

### 10.2 外部任务对照

先招募 6–8 位符合画像的外部用户作为发现问题的小样本，至少一半非熟人。给两个等价任务并交叉顺序：

- 用自己的常用工具，从既有资料中找出两条依据，完成一段技术说明并保留来源。
- 用 Paperin 完成等价任务，保存、关闭重开、导出，再在接收方软件中检查。

观察总耗时、有效操作、求助次数、来源正确性、漏图/断链、是否愿意下次继续。允许对照工具使用平时的插件配置，不能故意剥夺竞品能力。失败、放弃和需要指导的任务都计入记录。

小样本用于发现方向，不替代既有验收协议的正式 12 人任务或成熟四周队列。条件具备后再按原指标口径执行，不能用这份路线降低安全或正式验收标准。

### 10.3 指标与决策

| 阶段 | 观察指标 | 初始决策信号 |
| --- | --- | --- |
| 当前两人 | 每人任务闭环、重复使用、真实阻塞 | 两人都能反复完成核心任务；没有未解释的内容损坏和误报成功 |
| 6–8 人发现轮 | 独立完成与失败原因 | 多数人能完成；若主要价值必须靠开发者反复讲解，先改入口/定位 |
| 正式 12 人对照 | 打开/保存/找回与资料复用 | 沿用协议至少 10/12 独立成功；配对耗时改善目标 30%，必须同时报告失败率 |
| 成熟试用队列 | 四周有效使用和资料复用 | 沿用协议各至少 20 名已激活用户，W4 有效留存目标 40%、复用 25%；报告人数和失访，不以小样本宣称 PMF |
| 商业实验 | 实际付款、退款和支持负担 | 真实非关联付款与持续使用优于意愿问卷；样本未成熟不外推收入 |

北极星建议为**每周用已有资料完成并实际使用一份文档成果的研究样本用户数**。没有复用的新文档也有价值，可作为辅助指标；下载量、启动次数、笔记数量、停留时长不是成果指标。

连续两轮仍没有用户主动重复核心任务时，先调整目标任务或入口，不用 AI、同步或新增图谱作为默认补救。

## 11. 增长路径：从可展示任务到可重复采用

近期的增长目标是获得高质量反馈，而不是制造下载峰值。最有价值的演示是一个完整案例：用旧排障笔记、接口说明和设计记录，写成一份带来源的技术方案，并交付给另一位读者。

建议采用三个低维护渠道：一篇真实工作流教程、一个不含私人数据的项目示例库、面向少量技术作者/项目文档维护者的邀请试用。优先从已有的 Typora、Obsidian、VS Code 用户中寻找有明确问题的人，提供共存指南与清晰的兼容边界。

首轮只读打开或副本试用，不要求迁移全部资料。判断渠道价值时记录合格试用、独立完成、次周继续、支持工时。若只有点赞与下载而没有任务，调整表达；若有人持续使用但需要大量指导，先改善产品，暂不扩大招募。

当前尚未执行联系、发帖、采购或付费投放。本报告是运营建议，不代表已获得用户增长或收入。

## 12. 商业化：先卖明确结果，再决定产品分层

### 12.1 市场给出的价格信号

Obsidian 核心应用可免费使用，收费项包括同步和发布，商业支持许可为自愿；Typora 是一次性购买模式，核查时官网显示单许可税前 14.99 美元、个人最多三台设备。这说明“编辑器收费”“免费核心加服务”都存在，但不能直接推导 Paperin 应采用哪一个价位。[Obsidian](https://obsidian.md/pricing)、[Typora 官网](https://typora.io/)、[购买说明](https://support.typora.io/purchase/)

尤其不能把“比 Obsidian 免费”或“比 MarkText 更便宜”作为价值主张。对个人产品而言，减少一次返工或持续节省文档维护时间，比功能个数更适合验证支付理由。

### 12.2 推荐的商业顺序

| 选项 | 初步匹配度 | 验证方式 |
| --- | --- | --- |
| 赞助/支持维护 | 低复杂度，适合早期 | 明确自愿支持，与数据可用性和功能安全分开；不能当稳定收入假设 |
| 专业交付能力 | 与现有模板、导出、集合较接近 | 先修质量，以真实技术文档样例测试是否有人为可重复交付付费 |
| 一次性桌面许可或年度维护 | 可以研究，当前未定 | 比较两种报价表达与维护负担，不先建立复杂授权系统 |
| 同步/AI 订阅 | 有持续成本、隐私与运维负担 | 需求和单位成本都验证后再考虑，不能靠免费补贴掩盖需求不足 |
| 团队部署/支持 | 后期选择 | 先有重复团队任务和付费意向，再评估交付人力 |

当前 `package.json` 标记 MIT，但基线中未找到受版本管理的根 LICENSE 文件。应补齐项目许可声明、权利来源与第三方分发材料的核查，再公开定义商业分层。本报告不据一个元数据字段判断全部授权关系，也不建议追溯限制已有授权。

核心数据读取、保存、恢复与迁出保持可用。商业价值应建立在专业结果、服务或增值能力上，不把“取回自己的文件”设计为付费门槛。

### 12.3 验证门槛与成本

先与完成过核心任务的用户讨论最近一次交付成本，提供真实样例，再做小规模实际付款实验。沿用既有商业验收方向：至少 5 位非关联用户真实付费，并观察 30 天退款、使用和支持成本；问卷愿付不算收入。

记录每位用户带来的直接成本与支持时间，使用实际记录计算，不预设无限期终身价值。没有价格和购买转化证据时，不建立收入预测表。连续两轮没有付款理由，暂停收费功能扩建，保留免费/开源维护路线或重新验证目标任务。

## 13. 进入团队市场的桥梁

“长期希望服务团队”可以从现在影响文件格式、导出和接口边界，但不应变成现在就实现完整协作后台。

| 阶段 | 用户得到的结果 | 前置条件 |
| --- | --- | --- |
| 个人作者 | 用自己的资料完成并维护文档 | 当前核心流程和可靠性达标 |
| 向团队交付 | 同事能读到完整 HTML/PDF/Markdown 成果与来源 | 输出保真、链接资源可携带；不依赖收件人安装 Paperin |
| 小团队试点 | 少量作者按明确规则交换、评审或维护同一套项目文档 | 至少 3 个团队重复提出相同任务；先与现有 Git/协作平台共存，避免盲建同步 |
| 团队产品 | 有身份、权限、审计、冲突策略、管理和支持责任 | 明确预算与专门维护产能；另做架构和业务验证 |

本地文件、无账号使用与组织权限管理是不同层面的能力。团队试点不能把共享目录直接包装为实时协作，也不能把多个个人许可当作企业治理产品。

## 14. 对现有战略和计划的修正

已有战略的“可靠保存、默认可用的复用、稳定交付”仍然有价值；本轮主要修正证据与资源模型。

| 既有表述/安排 | 本轮核对 | 应作调整 |
| --- | --- | --- |
| 搜索预览—插入—返回尚未形成完整工程证据 | 当前 AppDialogs、来源引用与位置恢复已接通 | S07–S09 转为边界修复、可发现性和用户验证，不重新实现 |
| 大文档失败基线仍作为当前已知事实 | 后续完成记录存在单机通过；本轮与历史必须分开 | 保留历史问题，但以当前验证结果判断，不让旧失败永久阻塞 |
| 首批画像偏技术文章作者 | 用户明确包含技术/项目文档维护，且已有六类模板 | 以技术与项目工作为共同任务，文章作者作为邻近客群 |
| 按一位工程师每周四个工程日估算 | 实际为每天两小时加周末 | 替换为每周约 20 小时计划容量与分阶段门槛 |
| 优先建设尚未存在的基础能力 | 发现主要差距为信任边界与输出保真 | 先处理 A01–A09，再安排新功能 |
| 核对主题门禁通过 | 有 37 项基线豁免，部分弱化文字仅记录 | 不能宣传九主题全面满足可访问性 |
| 原型与维护文档全部可用 | README/package 仍引用不存在的 `design/soft-workbench`；部分行数已滞后 | 清理失效入口，让用户与贡献者能复现真实状态 |

保留 S00–S17 的追踪编号：A01/A02 对应 S01/S02，A05/A06 对应 S03/S07，输出 A03/A04 对应 S10，界面与草稿对应 S05/S09，发行对应 S04/S14，维护债务对应 S17。S13/S15/S16 的用户、增长、商业验证仍未由代码代替。

本文提供新的决策依据，不自动宣告原任务完成，也不降低已有数据安全、测试和正式发布门禁。后续实现应把对应任务逐条绑定复现、修复、测试、文档与提交。

## 15. 接下来应形成的四份真实证据

第一份是**可信工程基线**：已确认问题的回归、门禁结果、适用平台候选测试及仍然存在的限制。

第二份是**两位现有用户的任务日记**：具体使用场景、成果、绕路、失败和反复使用理由，持续两周即可开始产生判断依据。

第三份是**可对照的完整案例**：从项目资料中找依据、带来源写作、安全保存并交付，原工具和 Paperin 都按正常配置完成。

第四份是**条件明确的下一阶段决定**：有外部重复使用再扩大；有真实专业价值再试收费；有共同团队任务与资源再进入团队产品。

战略成功的近期标志，是外部用户在没有开发者指导时，用自己的 Markdown 资料完成真实工作，并愿意在下一次任务继续使用 Paperin。现有代码已经足以开始朝这个目标收敛；最重要的投入是让结果可信、流程连续、价值可观察。
